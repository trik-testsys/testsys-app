# Модуль `testsys-infra:grpc`

Модуль реализует порт `Grader` для проверки Решений через gRPC. Документ описывает компоненты адаптера и настройки для
разработчиков и тех, кто собирает приложение. Поведение проверки описано в
[features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented), контракт — в
[Grading.kt](../../testsys-domain/src/main/kotlin/tech/testsys/domain/contract/Grading.kt).

## Компоненты

Проверяющий узел — внешний gRPC-сервис, который запускает Решение в выбранной версии TRIK Studio. Протокол поставляет
`trik.testsys.grading:protos:1.2.0.RELEASE`; идентификаторы Посылки и результата имеют тип `int64`. В `File.name`
Полигона передаётся строковое значение `TestId`. Узел возвращает его в `FieldResult.name`.

| Компонент | Назначение |
|-----------|------------|
| `api/BalancingGrader` | Реализация порта и приём запросов |
| `api/GrpcConfiguration` | Бины адаптера и настройки по умолчанию |
| `internal/GradingFunctions` | Подготовка protobuf с явным чтением файлов, выбор узла и проверка ответа |
| `internal/JsonLogParser` | Разбор JSON-логов без IO; реализация расширяемого `LogParser` |
| `internal/GradingCoordinator` | Очередь, попытки, синхронизация и уведомления |
| `internal/GradingNodeManager` | Каналы узлов и фоновый кеш статусов |
| `internal/GrpcNodeClient` | Асинхронные RPC с предельным сроком |
| `internal/GradingPersistenceService` | Загрузка через доменные репозитории и транзакционное сохранение |

Источники версии TRIK Studio для подготовки Посылки описаны в
[features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

При подготовке protobuf `encodeSubmission` читает файлы Решения и Полигонов через `FileContentReader`.

`checkResult` проверяет имена файлов логов и видеозаписей через `TextLimits` до передачи результата на сохранение.
Правило отказа определено в [testsys.dev.grading.balancing](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

`GradingPersistenceService` открывает транзакции через `TransactionOperations`, который предоставляет приложение;
модуль `database` поставляет реализацию, повторяющую транзакцию при конфликте. Подготовка Посылки — чтение Тура,
Задачи или запроса проверки, Решения и Полигонов и перевод Посылки в очередь — выполняется в одной транзакции,
поэтому сервис собирает согласованный снимок данных.

`GradingPersistenceService` использует `TaskValidationRequestRepository.findBySubmissionId` для Авторских Посылок.
Авторские Посылки проверяются на Полигонах снимка запроса. Перед отправкой сервис сверяет
позицию Посылки, программу, автора, Задачу и версию TRIK Studio со снимком.
Последующие изменения или фиксация Задачи не меняют этот набор Полигонов.
Отсутствие связанного запроса валидации — ошибка подготовки. Текущая Задача для Авторской Посылки не загружается.

Внутренний API помечен `InternalGrpcApi`. Подготовленные Посылки попадают в блокирующую FIFO-очередь. Отдельный поток
отправки забирает контекст через `take`, выбирает узел по кешу статусов и отправляет запрос. Пока свободного узла нет,
поток ждёт до `pollInterval`, ограниченного оставшимся общим сроком. Пустая очередь блокирует поток отправки.

Координатор последовательно готовит Посылки, отправляет RPC и обрабатывает ответы в выделенном
`ScheduledExecutorService`. Поток отправки работает в отдельном `ExecutorService` и ждёт завершения шага отправки
перед следующим контекстом. Фоновый опрос статусов работает в отдельном `ScheduledExecutorService`; ответы поступают
асинхронно.

Кеш статусов не выполняет сетевых вызовов при чтении. Выбор узла использует максимум его сообщённой очереди и числа
локальных отправок, делённый на ёмкость. Узел с полной очередью новых отправок не получает. Транспортный повтор
возвращает подготовленный контекст в конец очереди.

Координатор хранит четыре состояния запуска: `Preparing` готовит данные, `Queued` ожидает отправки, `InFlight` содержит
текущую попытку RPC, `Saving` хранит принятый результат и таймер повторного сохранения. Подготовленные данные обязательны
в `Queued` и `InFlight`; результат обязателен в `Saving`. Переход создаёт новый объект состояния. Ответы RPC и таймеры
сохранения принимаются только для текущего объекта. Таймер общего срока проверяет объект `RunContext`, который
сохраняется при переходах между состояниями одного запуска. Поэтому старый таймер не затрагивает последующую перепроверку.

При `UNAVAILABLE` менеджер записывает `Unreachable` в кеш только для экземпляра регистрации узла текущей попытки.
Опрос запоминает объект состояния перед вызовом RPC и публикует ответ через `compareAndSet`: изменение кеша после
начала опроса не позволяет устаревшему ответу восстановить доступность. Признак незавершённого опроса снимается и
при отклонённом ответе, поэтому следующий опрос может обновить состояние. Политика исключения и восстановления
узла описана в [features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

`GrpcConfiguration` подключается приложением. Приложение предоставляет `TransactionOperations`
и доменные репозитории, включая `ContestRepository` и `TaskValidationRequestRepository`.
Начальный список узлов задаётся в [настройках](#настройки); во время работы узлы добавляются через `Grader.addNode`.
Закрытие контекста
прерывает поток отправки, останавливает `ExecutorService` и `ScheduledExecutorService`, отменяет RPC и закрывает
каналы. `removeNode` отменяет незавершённую попытку и возвращает контекст в очередь; повтор учитывает прежний лимит времени.

## Настройки

Значения по умолчанию загружаются из [grading-defaults.properties](src/main/resources/grading-defaults.properties).
Приложение может переопределить их через Spring Environment. Интервалы задаются в формате ISO-8601 `Duration`.

| Свойство | По умолчанию | Назначение |
|----------|--------------|------------|
| `testsys.grading.nodes` | Пустая строка | Начальный список gRPC-адресов Проверяющих узлов через запятую |
| `testsys.grading.max-attempts` | `3` | Общее число транспортных попыток запуска |
| `testsys.grading.total-timeout` | `PT30M` | Срок подготовки, ожидания и проверки |
| `testsys.grading.rpc-timeout` | `PT10M` | Предельный срок отдельной проверки, ограниченный оставшимся общим сроком |
| `testsys.grading.status-timeout` | `PT5S` | Предельный срок опроса статуса |
| `testsys.grading.poll-interval` | `PT5S` | Интервал фонового опроса |
| `testsys.grading.max-message-bytes` | `400000000` | Максимальный размер входящего gRPC-сообщения |
| `testsys.grading.should-record-video` | `true` | Запрашивать видеозапись проверки |

Список узлов задаётся одной строкой в properties, YAML или аргументе командной строки приложения.
Например: `testsys.grading.nodes=grader-1:50051,grader-2:50051`.
Переменная окружения для того же списка — `TESTSYS_GRADING_NODES=grader-1:50051,grader-2:50051`.

Пробелы по краям адресов удаляются, одинаковые адреса регистрируются один раз. Пустая строка или строка из пробелов
означает отсутствие начальных узлов. Пустой элемент непустого списка, в том числе после завершающей запятой,
останавливает запуск с ошибкой, содержащей имя свойства. Адрес передаётся gRPC как target без дополнительного разбора;
запятая внутри адреса не поддерживается.

`GrpcConfiguration` регистрирует узлы до запуска фоновой работы координатора. До первого ответа на опрос их состояние —
`Unknown`; доступность узлов не проверяется при регистрации. Если создание клиента завершается ошибкой, координатор
закрывает уже созданные каналы и останавливает свои исполнители, а запуск приложения завершается ошибкой.
Список читается при запуске; изменение конфигурации требует перезапуска приложения.

## Резервирование и сохранение

Координатор резервирует идентификатор Посылки до загрузки данных. Репозитории сохраняют итог и обновляют текущий
статус Посылки в одной транзакции. Резерв снимается после фиксации транзакции, затем вызываются подписчики;
ошибка одного подписчика не мешает остальным. Откат метаданных не удаляет уже записанные внешним `FileBlobStorage` блобы.

Ошибка сохранения оставляет результат и резерв в памяти для повторного сохранения, без повторного RPC.
Повтор сохранения назначается отдельной одноразовой задачей через `pollInterval`.

## Сроки проверки

Общий срок отсчитывается от приёма запроса и задаётся одноразовой задачей. Предельный срок RPC ограничен оставшимся
общим сроком. Принятый результат сохраняется и после истечения срока, если хранилище временно недоступно.
Завершение отменяет таймеры.

Общий срок проверяется между задачами координатора. Если доменный репозиторий блокирует загрузку или сохранение,
проверка сроков других Посылок ждёт окончания этого вызова. Приложение должно ограничивать время запросов к хранилищу.
RPC и фоновый опрос используют собственные предельные сроки независимо от таких задержек.

## Хранение в памяти

Очередь, кеш и защита от дубликатов живут в памяти одного экземпляра приложения. После перезапуска они не восстанавливаются.
