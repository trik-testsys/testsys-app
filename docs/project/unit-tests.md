# Модульные тесты

Документ фиксирует, как в `testsys-app` пишутся модульные тесты: инструменты, расположение и имена, что должен
проверять тест, его структура и общие рекомендации. Он предназначен для всех, кто пишет или ревьюит тесты.

Правила оформления из этого документа действуют и для интеграционных тестов. Что именно проверять в тестах
сущностей, маппингов и адаптеров и какие базовые классы для этого есть — в шаге «Тесты» гайдов
[implement-entity.md](../guides/implement-entity.md) и [implement-port.md](../guides/implement-port.md). Команды
запуска — в разделе «Сборка» в [structure.md](structure.md), остальной стиль кода — в [code-style.md](code-style.md).

## Инструменты

- Фреймворки: **JUnit 5** и **MockK** (`@ExtendWith(MockKExtension::class)`, `@MockK`, `@InjectMockKs`).
- Проверки — через `org.junit.jupiter.api.Assertions`.
- Тестовые данные создаются через DSL билдеров и тестовые хелперы, а не через конструкторы.

## Расположение и имена

- Тестовый класс называется `<Class>Tests` и лежит в том же пакете, что и тестируемый класс.
- Тесты одного метода группируются во вложенный класс: `@Nested inner class <Method>Tests`.
- Имя теста — предложение в обратных кавычках, начинающееся с `should`: `` `should create task with provided name` ``.

## Что проверяет тест

Каждый тест проверяет **один** сценарий одного из видов:

| Вид        | Что проверяет                                                                                                                                                   | Пример имени                                                                  |
|------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| Happy path | Основные успешные сценарии с корректными входными данными                                                                                                       | `should create task with provided name and description`                       |
| Edge case  | Граничные и особые входные данные: пустые коллекции, `null`, минимум и максимум, дубликаты, отсутствующие ссылки                                                | `should attach exercise for another language if task already has an exercise` |
| Инвариант  | Правило предметной области, которое выполняется всегда (термины и правила — в [definitions.md](../domain/definitions.md), [features.md](../domain/features.md)) | `should move Committed task to Uncommitted when resource is attached`         |
| Error      | Отказ: неверные аргументы, недостаточная Роль, недопустимое состояние, устаревшая версия                                                                        | `should raise MissedDeveloperRoleError if user is not a Developer`            |

- Метка вида в имени не пишется: из имени должно быть понятно, какой сценарий проверяется, при каких условиях
  и какой ожидается результат. Имя вроде `` `should work` `` или `` `should create task 2` `` этого не сообщает.
- Условие сценария пишется в имени явно (`if …`, `when …`, `with …`): оно отличает edge case и error от happy path.
- Если тест проверяет несколько видов сразу, разделите его на несколько тестов.
- Тесты операции покрывают каждое требование её фичи из [features.md](../domain/features.md), включая доступ
  по Ролям, и её error-сценарии.

### Регрессионные тесты

При исправлении дефекта рекомендуется добавить тест, который его воспроизводит.

- Тест помечается `@Tag("regression")`, чтобы регрессионные тесты можно было найти и запустить отдельно.
- Имя описывает правильное поведение, как у любого другого теста, а не сам дефект или исправление.
- Над тестом — комментарий со ссылкой на issue или PR с описанием дефекта.
- Тест должен падать на коде до исправления и проходить после него.

```kotlin
// https://github.com/trik-testsys/testsys-app/issues/<N>
@Test
@Tag("regression")
fun `should keep contests of a task when its name is updated`() { /*content*/ }
```

## Структура теста

Тест строится по схеме **Arrange — Act — Assert**:

1. **Arrange** — подготовка: входные данные, моки, состояние.
2. **Act** — ровно одно действие: вызов проверяемого метода.
3. **Assert** — проверки результата или побочного эффекта.

- Блоки разделяются пустой строкой; комментарии `// Arrange`, `// Act`, `// Assert` не пишутся.
- Если подготовка не нужна, блока Arrange нет.
- Для error-сценария Act и Assert допустимо объединить в проверке исключения: вызов находится внутри неё.
- Подготовка, общая для **всех** тестов класса, выносится в `@BeforeEach`; подготовка одного сценария остаётся
  в тесте, чтобы сценарий читался без переходов по файлу.

Образец — [DeveloperOperationsTests.kt](../../testsys-operation/src/test/kotlin/tech/testsys/operation/user/DeveloperOperationsTests.kt).

## Рекомендации

### Надёжность

- **Независимость.** Тесты не зависят друг от друга и от порядка запуска; изменяемое состояние между тестами
  не разделяется.
- **Детерминированность.** Без текущего времени, случайных значений, сети, файловой системы и `Thread.sleep`:
  время и идентификаторы задаются фиксированными значениями.
- **Скорость.** Модульный тест не поднимает Spring-контекст и БД; для этого есть интеграционные тесты.
- **Тест должен уметь падать.** Убедитесь, что новый тест падает, если сломать проверяемое поведение.
  Тест, который проходит при любой реализации, ничего не проверяет.

### Что и как проверять

- Проверяйте **поведение через публичный API**, а не детали реализации: не обращайтесь к `private`-членам
  через reflection и не завязывайтесь на порядок внутренних вызовов.
- Проверки конкретные: ожидаемые значения, тип исключения, состояние результата. `assertNotNull` или
  «не упало» — недостаточная проверка.
- Ожидаемое значение задаётся явно, а не вычисляется той же логикой, что и в проверяемом коде.
- Несколько `assert` в одном тесте допустимы, если они проверяют один результат одного действия.

### Данные и моки

- В тесте явно задаются только данные, важные для сценария; остальное берут на себя хелперы с разумными
  значениями по умолчанию. Так из теста видно, от чего зависит результат.
- Мокаются порты и другие внешние зависимости, а не доменные объекты: доменные объекты создаются через DSL.
- `verify` вызова мока пишется, только если сам вызов и есть проверяемое поведение (например, сохранение);
  если результат виден по возвращаемому значению, проверяется значение.

### Читаемость

- Без логики в тестах: без `if`, циклов и `try/catch`. Один сценарий с разными входными данными оформляется
  `@ParameterizedTest`.
- Повторяющаяся подготовка выносится в тестовые хелперы, повторяющиеся проверки — в assertion-хелперы
  (например, `assertRaises`).
- Не коммитьте закомментированные тесты; `@Disabled` допустим только с причиной в аргументе аннотации.
