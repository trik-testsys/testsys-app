# Служебные настройки

Модуль `testsys-infra:settings` хранит общий действующий снимок и управляет применением служебных настроек.
Он также объявляет контракт хранения реестра Проверяющих узлов.
Документ описывает источники, проверки, переключение и восстановление для разработчиков и эксплуатации.
Хранение описано в [database](../database/README.md), страница — в [app](../../testsys-web/app/README.md).

## Значения и источники

[SettingKey](src/main/kotlin/tech/testsys/infra/settings/api/SettingKey.kt) перечисляет все 16 сохраняемых свойств.
Произвольные ключи отклоняются. БД хранит только явные переопределения; затем выбирается Environment,
затем значение по умолчанию каталога. Разбор выполняется после выбора источника, поэтому неверное
перекрытое значение Environment не мешает запуску. Публичное Сообщество задаётся при запуске и доступно
только для просмотра. Настройки отправки почты в каталог не входят.

Числовые лимиты положительны; лимит Участников и предел времени Диагностики допускают ноль.
Длительности положительны. Общий срок проверки, RPC-срок, timeout статуса и интервал опроса должны помещаться
в наносекунды. Срок подтверждения и TTL приглашений проверяются при сложении с `Instant`, возраст файлов —
при вычитании. Форма принимает ISO-8601.
Для исходной настройки возраста файлов также поддерживаются единицы Spring. Префикс баллов непустой;
пробелы сохраняются. Полный набор проверяется до запуска потребителей и перед применением.

## Снимки потребителей

| Потребитель | Когда получает значения |
|-------------|-------------------------|
| Добавление Участников | Последующее добавление; существующих Участников не удаляет |
| Подтверждение почты | Создание или перезапись запроса; пара значений закрепляется на транзакцию |
| Коды-приглашения | Создание, замена или продление |
| Проверка | Четыре параметра фиксируются при приёме и сохраняются до завершения |
| Опрос узлов | Интервал перепланируется; следующий status RPC получает текущий timeout |
| Размер сообщения gRPC | Только новый процесс; все его каналы используют один действующий предел |
| Диагностика | Одна пара значений до чтения файла на каждый вызов |
| Очистка файлов | Один снимок на явный проход; сохранение настройки проход не запускает |

## Применение и ошибки

`SettingsService` сериализует изменения и сверяет ревизию формы. Неизменённые поля не становятся
переопределениями. Ресурсы нового опроса подготавливаются до записи и проверяют идентичность опубликованного
снимка. До публикации продолжает работать прежнее расписание. БД одной отдельной транзакцией сохраняет
весь набор, новую ревизию и `changeId`. Затем holder одной атомарной публикацией переключает динамические
значения. Освобождение прежних ресурсов не влияет на результат применения. Очередь и каналы сохраняются.

При ошибке подготовки записи нет. После ошибки commit отдельное чтение определяет исход по `changeId`.
Подтверждённый rollback сохраняет прежний набор. Зафиксированный кандидат компенсируется отдельной
CAS-записью прежних переопределений, включая их отсутствие. Ревизия продолжает расти.
Компенсация не перезаписывает неизвестное изменение. Прежний действующий снимок и его ресурсы сохраняются.

Если чтение не определило исход commit или компенсации, runtime продолжает работать с прежним известным
снимком. Дальнейшие изменения блокируются до перезапуска. Страница явно показывает неопределённость
сохранённого состояния; успешный rollback в этом случае не заявляется.

## Запуск и восстановление

Приложение создаёт один `RuntimeSettings` в родительском контексте до потребителей. Ошибка чтения БД
или неверные сохранённые данные прерывают запуск. После потери процесса новый holder берёт последний
зафиксированный payload: после commit кандидата — кандидат, после commit компенсации — прежние значения.
Отдельной записи «применено» нет. Проверки durable checkpoints моделируют потерю памяти; это не OS crash-тест.

Самостоятельные database, grpc и diagnostics используют прежнюю локальную конфигурацию без общего holder.
Полное приложение явно импортирует `SettingsConfiguration`; конфигурация операций требует общего holder.
Один процесс является единственным поддерживаемым писателем. Прямое редактирование технической таблицы
не является способом применения настроек.

## Реестр Проверяющих узлов

[GradingNodeStore](src/main/kotlin/tech/testsys/infra/settings/api/GradingNodeStore.kt) хранит записи
`StoredGradingNode`: адрес и признак участия в проверке. Каждая операция — отдельная завершённая транзакция.
`add` и `remove` идемпотентны, `setActive` сообщает об отсутствии адреса. Исключение записи может скрывать commit,
поэтому вызывающий перечитывает реестр. Хранение реализовано в [database](../database/README.md#служебные-настройки),
протокол применения к грейдеру — в [grpc](../grpc/README.md#реестр-узлов).
