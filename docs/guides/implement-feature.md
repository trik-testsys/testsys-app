# Реализация фичи

Гайд описывает, как реализовать пользовательскую фичу из раздела `testsys.user` в
[features.md](../domain/features.md): от проверки её спецификации до операции, тестов и статуса фичи. Он
предназначен для разработчиков, которые берутся за фичу.

Гайд не повторяет общие правила: устройство операций, модель ошибок и вспомогательные функции — в
[testsys-operation/README.md](../../testsys-operation/README.md), стиль кода и KDoc — в
[code-style.md](../project/code-style.md), тесты — в [unit-tests.md](../project/unit-tests.md), термины — в
[definitions.md](../domain/definitions.md), сборка — в [structure.md](../project/structure.md). Недостающие
сущности и порты добавляются по [implement-entity.md](implement-entity.md) и [implement-port.md](implement-port.md).
Веб-часть фичи (страница `Page`) в гайд не входит.

**Спецификация идёт первой.** Код реализует то, что написано в [features.md](../domain/features.md). Если
спецификация неточна, неполна или противоречит другим фичам, сначала исправляется она, а потом пишется код.

## 1. Проверить и уточнить спецификацию

Прочитайте фичу целиком вместе со связанными с ней описаниями: фичей сущности (`testsys.entity.*`),
`authorization`-фичей Роли и другими фичами над теми же сущностями.

Спецификация достаточна, если по ней без догадок отвечаются вопросы:

| Вопрос                          | Что должно следовать из текста                                                     |
|---------------------------------|------------------------------------------------------------------------------------|
| Кто выполняет                   | Роль — из префикса кодификатора                                                    |
| К чему есть доступ              | Над какими сущностями разрешено действие («созданной им Задаче»), со ссылкой на `authorization`-фичу Роли, если она это определяет |
| Что указывает Пользователь      | Все входные данные; какие из них обязательны                                       |
| Что происходит                  | Что создаётся, изменяется или возвращается                                         |
| Как меняются состояния          | Переходы состояний сущностей, например «является изменением Задачи» для `testsys.entity.task` |
| Какие ограничения               | Условия, при которых действие допустимо («не более 1 Условия»)                     |
| Что при отказе                  | Каждый отказ следует из текста: нет доступа, нет сущности, нарушено ограничение, недопустимое состояние |

Типичные дефекты спецификации:

- **неточность** — формулировку можно понять двумя способами;
- **неполнота** — ответа на вопрос из таблицы нет, например операции нужны входные данные, которых нет в тексте фичи;
- **противоречие** — фича расходится с фичей сущности, `authorization`-фичей или другой фичей;
- **термин** — используется понятие, которого нет в [definitions.md](../domain/definitions.md).

Как исправлять:

- Уточнение, которое прямо следует из других фич и не меняет поведение для пользователя, вносится в
  [features.md](../domain/features.md) сразу.
- Изменение поведения для пользователя или выбор между несколькими разумными вариантами обсуждается с командой
  **до** написания кода.
- Новый термин добавляется в [definitions.md](../domain/definitions.md).
- Если решение по части фичи не принято, эта часть не реализуется, а в фиче явно пишется, что она не
  зафиксирована.
- Правки спецификации входят в тот же PR, что и реализация. Формат записи фичи — в разделе «Структура фичи»
  в [features.md](../domain/features.md).

## 2. Проверить доменную модель и порты

- Сущности, их данные и состояния, которые использует фича, должны быть в `testsys-domain`. Если сущности
  нет — добавьте её по [implement-entity.md](implement-entity.md).
- Для загрузки и сохранения нужны порты хранения; для обращения к внешним системам — другие порты. Если порта
  нет — объявите его по [implement-port.md](implement-port.md).
- Если нужный порт ещё не передан в класс операций Роли, добавьте его параметром конструктора.

## 3. Объявить ошибки операции

Правила объявления — в разделе «Объявление ошибок» в
[testsys-operation/README.md](../../testsys-operation/README.md).

- Заведите `sealed interface <Operation>Error` в регионе класса операций Роли.
- Каждому отказу из шага 1 соответствует ровно одна конкретная ошибка. Существующие ошибки
  (`AuthorizationError`, `<Entity>NotExistsError`) переиспользуются: добавьте им новый интерфейс.
- Ошибка без отказа в спецификации — признак того, что шаг 1 не закончен.

## 4. Реализовать операцию

Метод добавляется в `<Role>Operations`, класс выбирается по префиксу кодификатора — см. раздел «Операции»
в [testsys-operation/README.md](../../testsys-operation/README.md).

1. Пометьте метод `@Feature("<кодификатор>")`, первым параметром примите Пользователя.
2. Оберните тело в `operation<T, <Operation>Error> { … }`.
3. Проверки выполняются в порядке: Роль → существование сущностей → доступ к ним → ограничения и допустимость
   состояния. Каждая проверка — `ensure` с ошибкой из шага 3.
4. Новые доменные объекты создаются через DSL, изменённые — через `withData` или хелперы из `util`.
5. Результат возвращается как `asSuccess()`.

Образцы — `createTask` (создание) и `attachStatement` (изменение с проверками) в
[DeveloperOperations.kt](../../testsys-operation/src/main/kotlin/tech/testsys/operation/user/DeveloperOperations.kt).

## 5. Написать тесты

Тесты операции — во вложенном классе `<Operation>Tests` в `<Role>OperationsTests`. Инструменты и хелперы
модуля — в разделе «Тесты» в [testsys-operation/README.md](../../testsys-operation/README.md), правила
имён, видов сценариев и структуры — в [unit-tests.md](../project/unit-tests.md).

Тесты выводятся из спецификации, уточнённой на шаге 1:

- на каждый отказ — error-тест с конкретной ошибкой из шага 3;
- на основной сценарий — happy path с проверкой результата и сохранения через порт;
- на каждое ограничение — edge case на его границе;
- на каждый переход состояния из фичи сущности — тест инварианта для каждого исходного состояния
  (например, New, Uncommitted и Committed для Задачи).

## 6. Обновить статус фичи

Статус в заголовке фичи меняется в том же PR. Значения статусов — в разделе «Структура фичи»
в [features.md](../domain/features.md).

- **Implemented** — реализованы все требования фичи.
- **Partially implemented** — реализована только часть, например операция без страницы. В описании фичи
  фиксируется, что сделано и что осталось.
