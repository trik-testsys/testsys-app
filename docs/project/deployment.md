# Развёртывание

Документ описывает, как запустить основное приложение `testsys-web:app` в окружениях Docker Compose dev, e2e
и production, как открыть Prometheus и Grafana этих окружений и как запустить Проверяющий узел. Он предназначен
для разработчиков, которые запускают полный стек локально, и для тех, кто разворачивает приложение на сервере.
Устройство образа, Compose-файлов, мониторинга и скрипта — в [deploy/README.md](../../deploy/README.md); сборка
Gradle — в разделе «Сборка» в [structure.md](structure.md#сборка). Устройство Проверяющего узла, настройка
конкретного HTTPS-прокси, оповещения мониторинга, e2e-сценарии и CI в документ не входят.

## Скрипт запуска

Окружения запускает `deploy/testsys.sh` в `sh` на Linux и в Git Bash на Windows из любого каталога:

```bash
sh deploy/testsys.sh <окружение> <команда> [опции] [<сервис>...]
```

Окружение — `dev`, `e2e`, `prod` или `node`. Цель `node` — отдельный Проверяющий узел, см.
[Проверяющий узел](#проверяющий-узел). Справку выводит `sh deploy/testsys.sh --help`.

| Команда | Окружения | Что делает |
|---------|-----------|------------|
| `up [--node] [--no-build]` | Все; `--node` и `--no-build` — кроме `node` | Собирает образ приложения и запускает окружение |
| `down [--node]` | Все; `--node` — кроме `node` | Удаляет контейнеры и сеть проекта, тома сохраняет |
| `clean [--rmi]` | `dev`, `e2e` | Удаляет и тома, и содержимое рабочего каталога узла, см. [Остановка и очистка](#остановка-и-очистка) |
| `logs [--node] [-f\|--follow] [<сервис>...]` | Все; `--node` — кроме `node` | Журналы сервисов; `-f` продолжает выводить новые строки |
| `ps [--node] [<сервис>...]` | Все; `--node` — кроме `node` | Контейнеры проекта, в том числе завершённые, и опубликованные порты |
| `config [--node]` | Все; `--node` — кроме `node` | Итоговая модель Compose после подстановки переменных |

Опции:

- `--node` запускает Проверяющий узел вместе с окружением `dev`, `e2e` или `prod`. Это не цель `node`: отличия —
  в разделе [Опция `--node` и цель `node`](#опция---node-и-цель-node). `up` и `down` без `--node` останавливают
  узел, запущенный ранее с `--node`;
- `--no-build` запускает уже собранный образ приложения без сборки, см. [Образ](#образ);
- `--rmi` для `clean` также удаляет образ приложения окружения;
- `--env-file <путь>` указывает файл переменных `prod` или `node`, см. [Файлы переменных](#файлы-переменных).
  Для `dev` и `e2e` опция не принимается.

Другие команды Compose, например `exec`, скрипт не выполняет. Их можно вызвать напрямую с теми же аргументами,
что передаёт скрипт, см. раздел «Скрипт» в [deploy/README.md](../../deploy/README.md#скрипт).

## Файлы переменных

| Файл | В Git | Где лежит | Что в нём |
|------|-------|-----------|-----------|
| `dev.env`, `e2e.env` | Да | `deploy/env/` | Значения окружения, общие для всех |
| `dev.local.env`, `e2e.local.env` | Нет | `deploy/env/`, создаётся из шаблона `<окружение>.local.env.example` | Значения вашей машины |
| Файл production | Нет | Вне checkout, создаётся из шаблона `deploy/env/prod.env.example` | Секреты и адреса production |
| Файл отдельного узла | Нет | Вне checkout на машине узла, создаётся из шаблона `deploy/env/grading-node.env.example` | Настройки узла |

Назначение каждой переменной описано комментарием в файле или шаблоне. Локальный файл dev создаётся так; затем
раскомментируйте в нём нужные строки:

```bash
cp deploy/env/dev.local.env.example deploy/env/dev.local.env
```

Значение из `<окружение>.local.env` перекрывает значение из `<окружение>.env`, а переменная оболочки — оба.
Пути машины, на которой запущен скрипт, на Windows записывайте как `C:/<путь>`.

Путь к файлу production или отдельного узла передайте в каждой команде опцией `--env-file <путь>` или один раз
переменной оболочки `TESTSYS_ENV_FILE`; опция важнее. Закройте доступ к файлу командой `chmod 600 <путь>` и храните
его в резервной копии.

## Что задать вручную

Остальные переменные уже имеют значения в файлах `deploy/env/` или в Compose-файлах.

| Запуск | Файл | Переменные |
|--------|------|------------|
| `dev`, `e2e` без узла | — | Ничего |
| `dev`, `e2e` с `--node` | `<окружение>.local.env` | `TESTSYS_GRADING_NODE_WORKSPACE`, см. [Рабочий каталог узла](#рабочий-каталог-узла) |
| `prod` | Файл переменных production | `TESTSYS_DB_PASSWORD`, `TESTSYS_MAIL_PASSWORD`, `TESTSYS_SUPERVISOR_ACCESS_TOKEN` (см. [Супервайзер](#супервайзер)), `TESTSYS_SERVICE_SECRET`, `TESTSYS_GRAFANA_URL` и `TESTSYS_GRAFANA_ADMIN_PASSWORD` (см. [Мониторинг в production](#мониторинг-в-production)), `TESTSYS_APP_CONFIG` (см. [Конфигурационный файл на сервере](#конфигурационный-файл-на-сервере)), `TESTSYS_LOG_DIR` (см. [Каталог логов на сервере](#каталог-логов-на-сервере)) |
| `prod` с `--node` | Файл переменных production | Те же, а также `TESTSYS_GRADING_NODE_TAG`, `TESTSYS_GRADING_NODE_WORKSPACE`; узел подключают по адресу `grading-node:8080`, см. [Проверяющие узлы в production](#проверяющие-узлы-в-production) |
| `node` | Файл переменных отдельного узла | `TESTSYS_GRADING_NODE_TAG`, `TESTSYS_GRADING_NODE_WORKSPACE`, `TESTSYS_GRADING_NODE_HOST_IP` (см. [Порт и безопасность](#порт-и-безопасность)) |

У каждого узла в production — свой `TESTSYS_GRADING_NODE_ID`. Обязательная переменная без значения останавливает
любую команду окружения, в том числе `down`, с её именем в сообщении.

По необходимости в `<окружение>.local.env` задают и другие значения, их примеры есть в шаблоне: занятые порты,
адрес Grafana при другом порте Grafana, внешние адреса узлов и скрипт начальных данных dev `TESTSYS_DB_SEED_SCRIPT`, см.
[Начальные данные dev](#начальные-данные-dev).

## Dev и e2e

Оба окружения запускают приложение, PostgreSQL и Mailpit, dev — ещё Prometheus и Grafana. Окружения могут работать
одновременно: у каждого свои проект, сеть, тома и порты. Порты публикуются только на `127.0.0.1`, их значения —
в `dev.env` и `e2e.env`. Кроме основного интерфейса приложение публикует служебный интерфейс и сервер метрик, см.
[Служебный интерфейс](#служебный-интерфейс) и [Метрики и мониторинг](#метрики-и-мониторинг).
PostgreSQL на хосте доступен пользователю `testsys` с паролем `testsys` в базе `testsys`.

Mailpit принимает все письма приложения и показывает их в веб-интерфейсе; внешним адресатам письма
не пересылаются. Параметры операций в `application-dev.yml` и `application-e2e.yml` совпадают со значениями
тестов модуля `app`. Отличаются только название Публичного Сообщества «Публичное Сообщество» и Псевдоним
Супервайзера «Супервайзер». Значения, сохранённые в служебном кабинете, перекрывают пять динамических параметров
операций из этих файлов; порядок источников — в разделе «Значения и источники»
в [settings/README.md](../../testsys-infra/settings/README.md#значения-и-источники).

Реестр Проверяющих узлов хранится в базе. При каждом запуске dev и e2e приложение заносит в реестр включёнными
адреса из `TESTSYS_GRADING_NODES`. По умолчанию это узел `grading-node:8080`, который запускается в проекте
окружения с `--node`. Узел, выключенный или удалённый в служебном кабинете, следующий запуск снова включит.
Без `--node` приложение запустится, но Посылки проверяться не будут, если в `<окружение>.local.env` не заданы
внешние узлы. Адреса прежних запусков остаются в реестре; лишние удалите в служебном кабинете.
Запуск dev с узлом:

```bash
sh deploy/testsys.sh dev up --node
```

Скрипт пересобирает образ приложения из текущего checkout, ждёт загрузки начальных данных и выводит её журнал.

Запуск e2e с узлом. Скрипт ждёт, пока приложение, PostgreSQL и Mailpit станут `healthy`; после этого стек готов
для тестового процесса, который запускается отдельно и обращается к опубликованным портам:

```bash
sh deploy/testsys.sh e2e up --node
```

Тестовый процесс отправляет все запросы с одного адреса. Поэтому в `application-e2e.yml` приложение не отклоняет
запросы сверх лимита частоты, а только пишет их в лог. Ограничение описано в разделе
«Ограничение частоты запросов» в [app/README.md](../../testsys-web/app/README.md#ограничение-частоты-запросов).

### Начальные данные dev

В dev можно указать SQL-скрипт начальных данных в `TESTSYS_DB_SEED_SCRIPT` в `dev.local.env`. Укажите абсолютный
путь на машине, на которой запущен скрипт. Скрипт выполняется после миграций Liquibase, создания Публичного
Сообщества и проверки Супервайзера, один раз на базу: при следующих `up` он пропускается, а изменённый скрипт
вызывает предупреждение. Скрипт не должен добавлять второго Супервайзера: если в базе два Супервайзера,
следующий запуск приложения завершится ошибкой.

Скрипт выполняется в одной транзакции, поэтому в нём не должно быть `BEGIN`, `COMMIT`, `ROLLBACK` и команд, которые
нельзя выполнить в транзакции. При ошибке изменения откатываются, `dev up` завершается с ошибкой, и следующий `up`
попробует применить скрипт снова. Чтобы применить изменённый скрипт, удалите данные командой `clean`
и запустите окружение снова. Как устроено применение — в разделе «Начальные данные dev»
в [deploy/README.md](../../deploy/README.md#начальные-данные-dev).

Если файла по указанному пути нет, на Linux `dev up` завершается с ошибкой. Docker Desktop создаёт на этом месте
каталог; удалите его и исправьте путь.

Вывод загрузки начальных данных и код её завершения:

```bash
sh deploy/testsys.sh dev logs db-seed
```

```bash
sh deploy/testsys.sh dev ps db-seed
```

## Production

Production-окружение запускает приложение, PostgreSQL, Prometheus и Grafana с `restart: unless-stopped`
и постоянными томами. PostgreSQL наружу не публикуется. HTTP основного интерфейса публикуется только
на `127.0.0.1:${TESTSYS_HTTP_PORT}` (по умолчанию `8080`) для HTTPS-прокси на том же сервере. Порты служебного
интерфейса, сервера метрик, Grafana и Prometheus тоже публикуются только на `127.0.0.1`, см.
[Служебный интерфейс](#служебный-интерфейс) и [Метрики и мониторинг](#метрики-и-мониторинг).

### Файл переменных production

1. Скопируйте `deploy/env/prod.env.example` в каталог вне репозитория и закройте доступ к копии командой
   `chmod 600 <путь>`.
2. Задайте в копии переменные из раздела [Что задать вручную](#что-задать-вручную).
3. Передавайте путь к файлу в каждой команде скрипта, см. [Файлы переменных](#файлы-переменных).

Команда `config` выводит итоговую модель Compose вместе с паролями, включая пароль администратора Grafana,
Кодом-доступа Супервайзера и кодом входа в служебный интерфейс из этого файла; не сохраняйте и не публикуйте
её вывод.

### Конфигурационный файл на сервере

1. Скопируйте `deploy/config/application-prod.example.yml` в каталог вне репозитория.
2. Замените в копии все заполнители `<…>`. Неотредактированный шаблон останавливает запуск приложения:
   заполнитель не преобразуется в значение свойства.
3. Дайте пользователю контейнера с UID `10001` право читать файл.
4. Укажите абсолютный путь к файлу в `TESTSYS_APP_CONFIG` в файле переменных production.

Обязательность и формат параметров операций — в разделе «Запуск и проверка»
в [app/README.md](../../testsys-web/app/README.md#запуск-и-проверка). Если файла по пути `TESTSYS_APP_CONFIG` нет,
на Linux запуск завершается с ошибкой.

### Каталог логов на сервере

1. Создайте каталог для файлов лога приложения вне репозитория.
2. Дайте пользователю контейнера с UID `10001` право писать в него, например `sudo chown 10001 <путь>`.
3. Укажите абсолютный путь к каталогу в `TESTSYS_LOG_DIR` в файле переменных production.

Приложение пишет в каталог файл `testsys.log` и сжатые файлы прошлых дней. Ротация описана в разделе «Логирование»
в [deploy/README.md](../../deploy/README.md#логирование). В dev и e2e файлы лога лежат в `deploy/logs/<окружение>/`.

### Образ

`up` собирает образ приложения из checkout и помечает его именем `TESTSYS_APP_IMAGE` (по умолчанию
`testsys-app:latest`). Чтобы запустить заранее собранный образ, задайте его имя в `TESTSYS_APP_IMAGE` и запустите
окружение с `--no-build`:

```bash
sh deploy/testsys.sh prod up --no-build --env-file <путь>
```

Если образа приложения нет у демона Docker, скрипт завершается с ошибкой до запуска сервисов. Опция работает
и в dev и e2e.

При публикации релиза GitHub образ приложения публикуется в Docker Hub как `testsystrik/testsys-app` с тегом
версии релиза, например `1.2.3`, и тегом `latest` (см. раздел CI в [structure.md](structure.md#ci)). Чтобы запустить
его, загрузите образ командой `docker pull testsystrik/testsys-app:<версия>`, задайте это имя в `TESTSYS_APP_IMAGE`
и запустите окружение с `--no-build`.

### Почта

Локального SMTP-сервиса в production нет. Приложение отправляет письма через внешний SMTP-сервер. Адрес, порт,
имя пользователя, адрес отправителя и флаги `smtp-auth`, `ssl` и `starttls` задаются в конфигурационном файле
на сервере, пароль — в `TESTSYS_MAIL_PASSWORD`. **Не удаляйте ключи `testsys.mail.*` из файла:** у свойств почты
есть значения по умолчанию, и без ключа приложение запустится с настройкой для локального SMTP-сервера без
авторизации. Смысл свойств и пример для implicit TLS — в разделе «Настройки»
в [mail/README.md](../../testsys-infra/mail/README.md#настройки).

### HTTPS-прокси

Прокси завершает TLS и передаёт запросы на опубликованный порт основного интерфейса. Основной интерфейс берёт
исходный адрес клиента и схему из заголовков `X-Forwarded-For` и `X-Forwarded-Proto`, поэтому прокси должен
устанавливать оба заголовка. По адресу из `X-Forwarded-For` основной интерфейс ограничивает частоту запросов
клиента; без заголовка все клиенты делят счётчик адреса прокси. Ограничение описано в разделе «Ограничение частоты
запросов» в [app/README.md](../../testsys-web/app/README.md#ограничение-частоты-запросов).
Служебный интерфейс за прокси не ставится, см.
[Служебный интерфейс](#служебный-интерфейс).
Требования к WebSocket для `/VAADIN/push` и sticky sessions при нескольких экземплярах приложения — в разделе
«Сборка веб-приложений» в [structure.md](structure.md#сборка-веб-приложений).

### Проверяющие узлы в production

Реестр Проверяющих узлов хранится в базе. В production его ведут в служебном кабинете на странице «Проверка»:
там узлы добавляют, включают, выключают и удаляют, см. раздел «Состояние проверки»
в [app/README.md](../../testsys-web/app/README.md#состояние-проверки). Адрес узла зависит от способа запуска:

| Режим | Опция скрипта | Адрес узла |
|-------|---------------|------------|
| Внешние узлы | Нет | `<адрес машины узла>:<опубликованный порт>`, см. [Проверяющий узел](#проверяющий-узел) |
| Узел на том же сервере | `--node` | `grading-node:8080` |

Переменная `TESTSYS_GRADING_NODES` необязательна. Адреса из неё через запятую кабинет предлагает добавить
действием «Импортировать из конфигурации». С `TESTSYS_GRADING_IMPORT_NODES=true` каждый запуск приложения
заносит эти адреса в реестр включёнными, в том числе узлы, выключенные или удалённые в кабинете. Как работает
импорт — в разделе [«Реестр узлов»](../../testsys-infra/grpc/README.md#реестр-узлов) grpc/README.md.

Запуск с внешними узлами:

```bash
sh deploy/testsys.sh prod up --env-file <путь>
```

Запуск с узлом на том же сервере:

```bash
sh deploy/testsys.sh prod up --node --env-file <путь>
```

## Проверяющий узел

Узел — отдельный проект [grading-node](https://github.com/trik-testsys/grading-node), образ
`testsystrik/grading-node`; тег — версия релиза узла, например `3.0.0`.

### Опция `--node` и цель `node`

Опция `--node` и цель `node` запускают один и тот же узел, но это разные способы запуска:

| | Опция `--node` | Цель `node` |
|---|---|---|
| Пример | `sh deploy/testsys.sh dev up --node` | `sh deploy/testsys.sh node up --env-file <путь>` |
| Что запускает | Окружение `dev`, `e2e` или `prod` вместе с узлом | Только узел, без приложения и PostgreSQL |
| Проект Compose | Проект окружения: `testsys-dev`, `testsys-e2e`, `testsys-prod` | Отдельный проект `testsys-grading-node` |
| Где работает узел | На машине приложения, в сети проекта окружения | На любой машине с Docker, обычно на другой |
| Адрес узла для приложения | `grading-node:8080` | `<адрес машины узла>:<опубликованный порт>` |
| Откуда берутся переменные узла | Из файлов переменных окружения | Из отдельного файла, созданного из `deploy/env/grading-node.env.example` |
| Публикация gRPC-порта | Не нужна: приложение обращается к узлу внутри сети проекта | Нужна, см. [Порт и безопасность](#порт-и-безопасность) |
| Подкаталог рабочего каталога | `<рабочий каталог>/testsys-<окружение>` | `<рабочий каталог>/testsys-grading-node` |
| Остановка | Командой `down` окружения | `sh deploy/testsys.sh node down --env-file <путь>`; `clean` не поддерживается |

Опцию `--node` нельзя передать цели `node`. Узел, запущенный целью `node`, не связан с окружениями: команды
окружений его не останавливают. Адрес такого узла в dev и e2e задаётся в `TESTSYS_GRADING_NODES`, а в production
его добавляют в служебном кабинете, см. [Проверяющие узлы в production](#проверяющие-узлы-в-production).

### Отдельный узел

Для отдельного узла скопируйте `deploy/env/grading-node.env.example` в каталог вне checkout на машине узла,
задайте в копии переменные из раздела [Что задать вручную](#что-задать-вручную) и запустите узел:

```bash
sh deploy/testsys.sh node up --env-file <путь>
```

На машине узла нужны `deploy/testsys.sh`, `deploy/compose.grading-node.yml`, `deploy/grading-node/entrypoint.sh`
и шаблон `deploy/env/grading-node.env.example` с тем же относительным расположением, например checkout репозитория.

### Порт и безопасность

gRPC узла работает без TLS и без аутентификации, а узел запускает присланные образы на демоне Docker своей машины
через `/var/run/docker.sock`. Поэтому любой, кто может подключиться к порту узла, запускает на этой машине
контейнеры. **Публикуйте порт только на частном интерфейсе и разрешайте подключение к нему только с машины
приложения.**

По умолчанию порт узла публикуется на `127.0.0.1` и на свободном порту хоста; с других машин такой порт недоступен.
Для отдельного узла задайте в его файле переменных адрес частного интерфейса и постоянный порт. Опубликованный порт
показывает команда `ps`:

```bash
sh deploy/testsys.sh node ps --env-file <путь>
```

### Образ TRIK Studio

Узел запускает каждую проверку в контейнере образа TRIK Studio. Столбец `tag` таблицы `ts_trik_studio_version`
хранит полную ссылку на этот образ `<репозиторий>:<тег>`, см. раздел
[«Версии TRIK Studio»](../../testsys-infra/database/README.md#версии-trik-studio) в database/README.md. Узел
передаёт значение в `docker run` без изменений, поэтому значение без репозитория, например `3.0.0`, Docker ищет как
`docker.io/library/3.0.0`, и каждая проверка завершается ошибкой. Демон Docker скачивает образ сам.

Если узел остановлен во время проверки, контейнер `run-<guid>` может продолжить работу. Остановите его командой
`docker stop run-<guid>`; после остановки Docker его удаляет.

### Рабочий каталог узла

`TESTSYS_GRADING_NODE_WORKSPACE` — каталог, в котором узел каждого проекта работает в своём подкаталоге. Требования:

- каталог существует; подкаталог проекта скрипт создаёт сам;
- путь абсолютный и указан так, как его видит демон Docker. На Linux это обычный путь хоста, в Docker Desktop
  для Windows путь `C:\<путь>` записывается как `/run/desktop/mnt/host/c/<путь>`;
- в пути нет запятых и пробельных символов: путь с пробелом ломает каждую проверку.

Узел пишет туда журналы и временные файлы проверок, их резервное копирование не нужно.

`TESTSYS_GRADING_NODE_INNER_TIMEOUT_SECONDS` должен быть меньше `testsys.grading.rpc-timeout` приложения, иначе
приложение прервёт вызов раньше узла; значение по умолчанию — в разделе «Настройки» в
[grpc/README.md](../../testsys-infra/grpc/README.md#настройки).

## Тома и резервное копирование

| Том | Содержимое |
|-----|------------|
| `postgres-data` | Данные PostgreSQL, в dev также отметка о применённых начальных данных |
| `files` | Файловое хранилище приложения |
| `prometheus-data` | Метрики Prometheus за 14 дней; только dev и production |
| `grafana-data` | Пользователи, пароли и настройки Grafana; только dev и production |

Docker добавляет к имени тома имя проекта, например `testsys-prod_postgres-data` и `testsys-prod_files`.
Конфигурационный файл на сервере храните в резервной копии вместе с файлом переменных production: в Git их нет.

Тома `prometheus-data` и `grafana-data` в резервную копию можно не включать. Без них пропадут история метрик
и учётные записи Grafana; при следующем запуске Grafana снова создаст администратора `admin` с паролем
из `TESTSYS_GRAFANA_ADMIN_PASSWORD`.

Строки базы данных ссылаются на файлы тома `files`. Хранилище только добавляет файлы и не перезаписывает их,
поэтому сначала снимите дамп базы, затем скопируйте том: копия будет содержать все файлы, на которые ссылается дамп.
Очистка сирот выполняется только в режиме обслуживания, см. раздел
[«Очистка сирот»](../../testsys-infra/database/README.md#очистка-сирот) в database/README.md.

Дамп базы снимается прямым вызовом Compose из корня checkout. Вызов передаёт те же Compose-файлы, что и скрипт,
в том числе файл мониторинга, см. раздел «Скрипт» в [deploy/README.md](../../deploy/README.md#скрипт):

```bash
docker compose -p testsys-prod --env-file <путь к файлу переменных> -f deploy/compose.yml -f deploy/compose.monitoring.yml -f deploy/compose.prod.yml exec -T postgres pg_dump -U testsys -d testsys --format=custom > testsys.dump
```

Архив тома файлов в текущем каталоге:

```bash
docker run --rm -v testsys-prod_files:/data:ro -v "$PWD":/backup postgres:17-alpine tar -C /data -czf /backup/testsys-files.tar.gz .
```

## Остановка и очистка

| Команда | Контейнеры и сеть проекта | Тома проекта | Рабочий каталог узла | Образ приложения |
|---------|---------------------------|--------------|----------------------|------------------|
| `down` | Удаляет, в том числе узел; в dev и production также Prometheus и Grafana | Сохраняет | Сохраняет | Сохраняет |
| `clean` | Удаляет, в том числе узел; в dev также Prometheus и Grafana | Удаляет `postgres-data` вместе с отметкой начальных данных и `files`, в dev также `prometheus-data` и `grafana-data` | Очищает подкаталог проекта | Сохраняет |
| `clean --rmi` | Удаляет, в том числе узел; в dev также Prometheus и Grafana | Удаляет | Очищает подкаталог проекта | Удаляет образ `testsys-<окружение>-app` |

Остановка dev с сохранением данных и полная очистка dev:

```bash
sh deploy/testsys.sh dev down
```

```bash
sh deploy/testsys.sh dev clean
```

`clean` работает только для dev и e2e и не трогает другие проекты Compose, сам каталог
`TESTSYS_GRADING_NODE_WORKSPACE` и подкаталоги других проектов. Запускайте очистку, когда проверок нет: временные
файлы работающей проверки тоже будут удалены. Без `TESTSYS_GRADING_NODE_WORKSPACE` рабочий каталог не очищается.

Контейнеры проверок `run-<guid>` после `down` дорабатывают и удаляются сами. Отдельный узел останавливается своей
командой; его подкаталог `testsys-grading-node` удаляйте вручную:

```bash
sh deploy/testsys.sh node down --env-file <путь>
```

### Остановка production

`sh deploy/testsys.sh prod down --env-file <путь>` удаляет контейнеры и сеть и сохраняет тома: скрипт не удаляет
тома production ни одной командой. Прямой вызов `docker compose … down -v` удаляет базу и файлы приложения без
возможности восстановления, а также историю метрик и учётные записи Grafana; перед ним снимите резервную копию, см.
[Тома и резервное копирование](#тома-и-резервное-копирование).

## Публичное Сообщество

Свойство `testsys.operation.community.public-community-id` обязательно в конфигурационном файле каждого
окружения. При первом запуске с пустой базой приложение создаёт Публичное Сообщество с этим ID и названием из
`testsys.operation.community.public-community-name`. Для существующей базы задайте ID уже созданного Публичного
Сообщества. Как приложение создаёт и проверяет запись — в разделе «Запуск и проверка»
в [app/README.md](../../testsys-web/app/README.md#запуск-и-проверка).

## Супервайзер

Псевдоним и Код-доступа единственного Супервайзера обязательны в каждом окружении: без них приложение
не запускается. В production Псевдоним задаётся свойством `testsys.operation.supervisor.name` в конфигурационном
файле на сервере, а Код-доступа — переменной `TESTSYS_SUPERVISOR_ACCESS_TOKEN` в файле переменных production.
В dev и e2e оба значения записаны в `application-dev.yml` и `application-e2e.yml`: Супервайзер этих окружений
входит по Коду-доступа `Supe-rvis-or00-0001`.

Чтобы сменить Код-доступа Супервайзера, задайте новое значение и перезапустите приложение: прежний Код-доступа
перестаёт действовать. Как приложение проверяет Супервайзера при запуске — в разделе «Запуск и проверка»
в [app/README.md](../../testsys-web/app/README.md#запуск-и-проверка).

## Служебный интерфейс

Служебный интерфейс — отдельный HTTP-сервер приложения со служебным кабинетом: служебными настройками, состоянием
проверки и поиском Пользователей. Его страницы описаны в разделе «Служебный контекст»
в [app/README.md](../../testsys-web/app/README.md#служебный-контекст). Compose публикует порт служебного интерфейса
только на `127.0.0.1` хоста; порт хоста задаёт `TESTSYS_SERVICE_HTTP_PORT`.

| Окружение | Адрес по умолчанию | Код входа |
|-----------|--------------------|-----------|
| `dev` | `http://localhost:8083/` | `local-service-secret-for-dev-and-e2e-environments-only-not-secret` |
| `e2e` | `http://localhost:8093/` | Тот же, что в dev |
| `prod` | `127.0.0.1:8081` сервера | Значение `TESTSYS_SERVICE_SECRET` из файла переменных production |

В dev и e2e код входа записан в `deploy/compose.dev.yml` и `deploy/compose.e2e.yml` и не секретен.

**Не ставьте служебный интерфейс за HTTPS-прокси и не публикуйте его порт на внешнем интерфейсе.** Сервер работает
по HTTP, игнорирует forwarded-заголовки и выдаёт cookie без `Secure`, см. раздел «Конфигурация запуска»
в [app/README.md](../../testsys-web/app/README.md#конфигурация-запуска). В production подключайтесь к нему через
SSH-туннель с вашей машины, затем откройте `http://localhost:8081/`:

```bash
ssh -N -L 8081:127.0.0.1:8081 <пользователь>@<сервер>
```

Туннель сразу к служебному интерфейсу, Grafana и Prometheus — в разделе
[Мониторинг в production](#мониторинг-в-production).

Код входа в production должен содержать не меньше 64 символов. Сгенерируйте его и запишите в
`TESTSYS_SERVICE_SECRET`:

```bash
openssl rand -hex 32
```

Чтобы сменить код, задайте новое значение и снова выполните `up`: Compose пересоздаст контейнер приложения,
и прежний код перестанет действовать.

Кнопка «Grafana» служебного кабинета открывает адрес из `TESTSYS_GRAFANA_URL`. В dev и production это Grafana
того же проекта, см. [Prometheus и Grafana](#prometheus-и-grafana). В e2e Grafana не запускается, но приложение
без адреса не запустится. Поэтому `e2e.env` задаёт адрес Grafana dev `http://localhost:3000/grafana/`: он открывается,
только если запущен dev, а метрик e2e эта Grafana не показывает.

## Метрики и мониторинг

Сервер метрик отдаёт `GET /actuator/prometheus` без входа; устройство — в разделе «Сервер метрик»
в [app/README.md](../../testsys-web/app/README.md#сервер-метрик). Compose публикует его только на `127.0.0.1` хоста;
порт хоста задаёт `TESTSYS_METRICS_HTTP_PORT`: в dev `8082`, в e2e `8092`, в production по умолчанию `8082`.

Dev и production запускают в своём проекте Prometheus и Grafana. Prometheus собирает метрики приложения того же
проекта внутри сети Compose, поэтому сбор не зависит от опубликованного порта метрик. В e2e мониторинга нет,
и метрики e2e не собираются. Как устроены сбор, Grafana и дашборды — в разделе «Мониторинг»
в [deploy/README.md](../../deploy/README.md#мониторинг).

### Prometheus и Grafana

| Окружение | Grafana | Prometheus |
|-----------|---------|------------|
| `dev` | `http://localhost:3000/grafana/` | `http://localhost:9090/` |
| `prod` | `127.0.0.1:3000` сервера с префиксом `/grafana/`, через SSH-туннель | `127.0.0.1:9090` сервера, через SSH-туннель |

Порты хоста задают `TESTSYS_GRAFANA_PORT` и `TESTSYS_PROMETHEUS_PORT`, в dev их значения — в `dev.env`.
`TESTSYS_GRAFANA_URL` — адрес этой Grafana в браузере: его открывает кнопка «Grafana» служебного кабинета, и по нему
Grafana строит свои ссылки. Путь этого адреса — префикс, по которому отвечает Grafana; по умолчанию `/grafana/`.
Если вы меняете `TESTSYS_GRAFANA_PORT` в `dev.local.env`, задайте там же `TESTSYS_GRAFANA_URL` с тем же портом.

### Учётные записи Grafana

У Grafana свои учётные записи, не связанные со служебным входом TestSys. Самостоятельная регистрация и анонимный
доступ выключены. Учётные записи хранятся в томе `grafana-data`: `down` их сохраняет, `clean` удаляет.

При первом запуске dev Grafana создаёт администратора `admin` с паролем `admin`. Войдите им и сразу смените пароль:
Grafana предлагает это после первого входа. Остальных пользователей создайте в разделе Administration → Users and
access → Users.

### Мониторинг в production

Пароль администратора `admin` задаёт `TESTSYS_GRAFANA_ADMIN_PASSWORD` в файле переменных production. Сгенерируйте
его:

```bash
openssl rand -hex 16
```

Grafana применяет пароль только при первом запуске, когда том `grafana-data` пуст. Позже меняйте пароль в самой
Grafana: новое значение переменной на существующую учётную запись не действует.

**Не ставьте Grafana и Prometheus за HTTPS-прокси и не публикуйте их порты на внешнем интерфейсе.** Prometheus
не требует входа, а Grafana работает по HTTP с адресом из `TESTSYS_GRAFANA_URL`. Подключайтесь к ним через
SSH-туннель вместе со служебным интерфейсом:

```bash
ssh -N -L 8081:127.0.0.1:8081 -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 <пользователь>@<сервер>
```

Затем откройте Grafana по адресу `http://localhost:3000/grafana/`, а Prometheus — по адресу `http://localhost:9090/`.
Задайте адрес Grafana `http://localhost:3000/grafana/` в `TESTSYS_GRAFANA_URL`: локальный порт туннеля должен совпадать
с портом этого адреса. Если на сервере заданы другие `TESTSYS_GRAFANA_PORT` или `TESTSYS_PROMETHEUS_PORT`, укажите
их после `127.0.0.1:` в соответствующей опции `-L`.

### Проверка сбора

Адреса ниже — значения dev по умолчанию. В production откройте Prometheus и Grafana через туннель, а сервер метрик
запросите на самом сервере.

1. Откройте `http://localhost:9090/targets`: цель `testsys` должна быть в состоянии `UP`.
2. Войдите в Grafana и откройте папку «TestSys». На дашборде проверки панель «Опрос TestSys» показывает
   «Доступен», на дашборде HTTP после нескольких запросов к TestSys появляются данные.
3. Запросите сервер метрик с заголовком OpenMetrics:

```bash
curl -H 'Accept: application/openmetrics-text;version=1.0.0' http://localhost:8082/actuator/prometheus
```

Ответ должен иметь тип `application/openmetrics-text`, заканчиваться `# EOF` и содержать `_created` для уже
созданных счётчиков и HTTP-гистограмм.

4. После запуска TestSys откройте один отсутствующий адрес основного интерфейса. Дождитесь успешного опроса.
   В таблице точек входа дашборда HTTP строка `NOT_FOUND` должна показать первый ответ 4xx; при единственном
   запросе этого ряда число запросов и число 4xx равны 1, доля 4xx — 100%. Выбранный период должен включать запрос.

Автоматическая проверка конфигурации описана в разделе «Проверка конфигурации»
в [deploy/README.md](../../deploy/README.md#проверка-конфигурации).
