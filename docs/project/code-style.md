# Стиль кода

Документ фиксирует единые соглашения о том, как писать Kotlin-код в `testsys-app`: язык, именование, идиомы,
обработку ошибок, комментарии и KDoc. Он предназначен для всех, кто пишет или ревьюит код.

Документ не описывает устройство модулей и сборку ([structure.md](structure.md)), тесты
([unit-tests.md](unit-tests.md)), а также пошаговое добавление сущностей и портов (гайды из перечня
в [docs.md](../docs.md)).

## Язык

| Где                                        | Язык        |
|--------------------------------------------|-------------|
| Идентификаторы, KDoc, комментарии в коде   | Английский  |
| Сообщения исключений и логов               | Английский  |
| Строки, которые видит пользователь         | Через модуль локализации, см. [localization/README.md](../../testsys-infra/localization/README.md) |

Язык документации — в [docs.md](../docs.md).

## Именование

- Сокращения пишем как слова: `wipContentId`, а не `WIPContentId`. Устоявшиеся сокращения проекта: `wip`, `jpa`, `id`.
- Имена отражают смысл в терминах предметной области ([definitions.md](../domain/definitions.md)): `developerSolutions`,
  а не `files2`.

## Идиомы Kotlin

### Неизменяемость

- По умолчанию `val` и read-only коллекции (`List`, `Set`, `Map`) в публичном API.
- Изменяемое состояние (`var`) допустимо только в билдерах и в JPA-сущностях там, где этого требует Hibernate.
- Доменные объекты обновляются созданием нового экземпляра (`X.withData { ... }`), а не мутацией.

### Типы

- Идентификаторы — `@JvmInline value class`, а не голые `Long`. Голые `Long` допустимы в JPA-слое и в сеттерах
  билдеров (`owner(42)`).
- Варианты состояния — `sealed interface`/`sealed class`, а не набор nullable-полей или флагов.
- `when` по sealed-типу пишется без ветки `else`, чтобы компилятор ловил новые варианты.
- Не используйте небезопасные приведения `as` — только `as?` или smart cast через `is`.

### Функции и выражения

- Для короткой функции с одним выражением используйте expression body. Образец — `TaskMapping.encodeStatus`
  в [TaskMapping.kt](../../testsys-infra/database/src/main/kotlin/tech/testsys/infra/database/internal/mapping/task/TaskMapping.kt).
- У публичных функций с expression body тип результата указывается явно, если он не очевиден из правой части.
- При вызове с несколькими параметрами одного типа, а также при создании доменных и JPA-объектов используйте
  **именованные аргументы**.
- Во вложенных лямбдах давайте параметрам имена вместо `it`.

### Видимость

- Делайте члены `private`, если они не нужны снаружи.
- Внутренний API модуля из `testsys-infra` помечается `@Internal...Api`.

### Порядок членов класса

- Среди функций сначала идут публичные и `override`, затем приватные.

## Ошибки и проверки

- Нарушение контракта аргументов — `require(...)` / `requireNotNull(...)` (`IllegalArgumentException`).
  Нарушение внутреннего состояния — `check(...)` / `checkNotNull(...)` (`IllegalStateException`).
  Недостижимая ветка — `error("...")`.
- Сообщение исключения содержит контекст: какая сущность, какое значение, что ожидалось. Образец —
  `loadTaskContent` в [TaskPersistenceAdapter.kt](../../testsys-infra/database/src/main/kotlin/tech/testsys/infra/database/api/persistence/adapter/task/TaskPersistenceAdapter.kt).
- Не ловите `Exception`/`Throwable` целиком, если можете поймать конкретный тип.

Модель ошибок операций — в разделе «Ошибки» в [testsys-operation/README.md](../../testsys-operation/README.md).

> Модель ошибок портов (исключения или доменный тип результата) пока не зафиксирована.

## Комментарии

- Комментарий в коде объясняет **почему**, а не **что**. Если комментарий пересказывает код — удалите его
  или переименуйте переменную.
- Закомментированный код не коммитим — он есть в истории git.
- Методы операций, реализующие пользовательскую фичу, помечаются `@Feature("testsys.…")` с кодификатором
  из [features.md](../domain/features.md).

## KDoc

### Где нужен KDoc

- KDoc обязателен на всех **публичных** классах, функциях и свойствах, в том числе на тривиальных функциях.
- На `private`, `internal` и `protected` членах KDoc необязателен: только описание, без `@since`.
- `override`-члены (включая все `build()` билдеров) KDoc не получают — он наследуется от базового объявления.
  `override val` в конструкторе не получает и `@property`.
- Локальные функции и классы внутри тела функции KDoc не получают.

### Форма

- Одно-два предложения. Без вторых абзацев, списков унаследованных членов, пояснений `NOTE`/`CAUTION`,
  пересказывающих то, что обеспечивает код, без `@see` и без пустых `@param x the x`.
- Порядок тегов: `@param` (сначала параметры типа), `@property`, `@return`/`@throws`, `@since`.
- Каждое публичное объявление заканчивается `@since %CURRENT_VERSION%`. Плейсхолдер пишется буквально,
  версия не подставляется.
- Параметры упоминаются в тексте как `[name]`. `@param` и `@return` пишутся, только если имени недостаточно:
  у портов в `contract`, у `load(...)`, `file(name, content)`, функций с двумя лямбдами и `Builder.build`.
- Каждый параметр типа описывается `@param T ...` в KDoc обобщённого класса или функции.
- Свойства описываются в KDoc **класса** через `@property`, а не блоком над свойством. Свойства companion
  object упоминаются в описании класса.
- У билдеров обязательные поля перечисляются в описании класса: «Required: [owner], [name].»
- Кодификатор фичи `testsys.*` упоминается, только если фича есть в [features.md](../domain/features.md).

### Ссылки `[...]`

- Нет ссылок от базового класса или интерфейса на наследников и на несвязанных потребителей
  (`Solution` не ссылается на `Submission`).
- Внутри агрегата ссылки ожидаются. Агрегат — сущность `X` и всё, что существует только ради неё: `XId`, `XData`,
  её sealed-типы состояний, данные Роли, sealed- и value-типы, используемые ровно одним `XData`. Все они ссылаются
  на `[X]`; `DomainId` ссылается на `DomainEntity`.
- Общие value-типы (`Score`, `FileData`, `TrikSupportedLanguage`) ни на кого не ссылаются.

### Типовые формулировки

| Что                      | Формулировка                                                                  |
|--------------------------|-------------------------------------------------------------------------------|
| Идентификатор            | `Identifier of a [Task].`                                                     |
| Данные                   | `Data of a [Task].`, `@property data the data of the task.`                   |
| Билдер данных            | `Builder of [TaskData]. Required: [owner], [name].`                           |
| Билдер сущности          | `Builder of [Task] entities. Required: [id], [createdAt], [data].`            |
| Необязательное поле      | ``@property name the name of the task, or `null` if not set yet.``            |
| Сеттер DSL               | `Sets [owner] from a raw id.`, `Sets [name].`                                 |
| Адаптер                  | `Persistence adapter of [Class] entities backed by [ClassJpaEntity].`         |
| Маппинг                  | `Mapping between [Class] and [ClassJpaEntity].`                               |

### Проверка

Структурные нарушения этих правил (нет KDoc или `@since`, KDoc над свойством или `override`, лишний `@see`,
слишком длинное описание и т. п.) находит скрипт [check_kdoc.py](../../scripts/check_kdoc.py), нужен Python 3.
Формулировки он не оценивает. Список кодов нарушений — в `--help`.

```bash
python3 scripts/check_kdoc.py testsys-domain/src/main/kotlin
```
