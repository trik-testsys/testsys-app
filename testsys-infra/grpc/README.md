# Модуль `testsys-infra:grpc`

Модуль реализует порт `Grader` для проверки Решений через gRPC и служебные API реестра узлов и состояния очереди.
Документ описывает компоненты адаптера, реестр, очередь и настройки для разработчиков и тех, кто собирает
приложение. Поведение проверки описано в
[features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented), контракт — в
[Grading.kt](../../testsys-domain/src/main/kotlin/tech/testsys/domain/contract/Grading.kt).

## Компоненты

Проверяющий узел — внешний gRPC-сервис, который запускает Решение в выбранной версии TRIK Studio. Протокол поставляет
`trik.testsys.grading:protos:1.2.0.RELEASE`; идентификаторы Посылки и результата имеют тип `int64`. В `File.name`
Полигона передаётся строковое значение `TestId`. Узел возвращает его в `FieldResult.name`.

| Компонент | Назначение |
|-----------|------------|
| `api/BalancingGrader` | Реализация порта и приём запросов |
| `api/GrpcConfiguration` | Бины адаптера и настройки по умолчанию |
| `api/GradingNodeRegistry` | Служебный API реестра узлов: обзор, добавление, участие, удаление и импорт |
| `api/GradingQueueMonitor` | Служебный снимок незавершённых проверок по состояниям координатора |
| `internal/GradingFunctions` | Подготовка protobuf с явным чтением файлов, выбор узла и проверка ответа |
| `internal/JsonLogParser` | Разбор JSON-логов без IO; реализация расширяемого `LogParser` |
| `internal/GradingCoordinator` | Очередь, попытки, синхронизация и уведомления |
| `internal/GradingNodeManager` | Мониторы опроса и регистрации участия в проверке с отдельными каналами, кеш статусов |
| `internal/GradingNodeRegistryCoordinator` | Протокол изменения реестра: порядок записи и шагов грейдера, исходы и блокировка |
| `internal/ConfiguredGradingNodeStore` | Реестр в памяти для грейдера без хранилища |
| `internal/GrpcNodeClient` | Асинхронные RPC с предельным сроком |
| `internal/GradingPersistenceService` | Загрузка через доменные репозитории и транзакционное сохранение |

Источники версии TRIK Studio для подготовки Посылки описаны в
[features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

При подготовке protobuf `encodeSubmission` читает файлы Решения и Полигонов через `FileContentReader`.

`checkResult` проверяет имена файлов логов и видеозаписей через `TextLimits` до передачи результата на сохранение.
Правило отказа определено в [testsys.dev.grading.balancing](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

`GradingPersistenceService` открывает транзакции через `TransactionOperations`, который предоставляет приложение;
модуль `database` поставляет реализацию, повторяющую транзакцию при конфликте. Подготовка Посылки — чтение Тура,
Задачи или запроса проверки, Решения и Полигонов и перевод Посылки в очередь — выполняется в одной транзакции,
поэтому сервис собирает согласованный снимок данных.

`GradingPersistenceService` использует `TaskValidationRequestRepository.findBySubmissionId` для Авторских Посылок.
Авторские Посылки проверяются на Полигонах снимка запроса. Перед отправкой сервис сверяет
позицию Посылки, программу, автора, Задачу и версию TRIK Studio со снимком.
Последующие изменения или фиксация Задачи не меняют этот набор Полигонов.
Отсутствие связанного запроса валидации — ошибка подготовки. Текущая Задача для Авторской Посылки не загружается.

Внутренний API помечен `InternalGrpcApi`. Подготовленные Посылки попадают в блокирующую FIFO-очередь. Отдельный поток
отправки забирает контекст через `take`, выбирает узел по кешу статусов и отправляет запрос. Пока свободного узла нет,
поток ждёт до `pollInterval`, ограниченного оставшимся общим сроком. Пустая очередь блокирует поток отправки.

Координатор последовательно готовит Посылки, отправляет RPC и обрабатывает ответы в выделенном
`ScheduledExecutorService`. Поток отправки работает в отдельном `ExecutorService` и ждёт завершения шага отправки
перед следующим контекстом. Фоновый опрос статусов работает в отдельном `ScheduledExecutorService`; ответы поступают
асинхронно.

Кеш статусов не выполняет сетевых вызовов при чтении. Выбор узла рассматривает только узлы, участвующие в проверке,
и использует максимум сообщённой очереди узла и числа локальных отправок, делённый на ёмкость. Узел с полной очередью
новых отправок не получает. Транспортный повтор возвращает подготовленный контекст в конец очереди.

Координатор хранит четыре состояния запуска: `Preparing` готовит данные, `Queued` ожидает отправки, `InFlight` содержит
текущую попытку RPC, `Saving` хранит принятый результат и таймер повторного сохранения. Подготовленные данные обязательны
в `Queued` и `InFlight`; результат обязателен в `Saving`. Переход создаёт новый объект состояния. Ответы RPC и таймеры
сохранения принимаются только для текущего объекта. Таймер общего срока проверяет объект `RunContext`, который
сохраняется при переходах между состояниями одного запуска. Поэтому старый таймер не затрагивает последующую перепроверку.

При `UNAVAILABLE` менеджер записывает `Unreachable` в монитор узла, только если регистрация попытки остаётся текущей.
Причину `Unreachable` для опроса и для сбоя отправки формирует одна функция `unreachableReason` в `GrpcNodeClient.kt`.
Причина — только имя кода gRPC `Status`, например `UNAVAILABLE`. Ошибка без gRPC-статуса даёт `UNKNOWN`, а завершённый
опрос без ответа — `INTERNAL`. Полное описание ошибки пишется в лог. `GrpcNodeClient` пишет первый сбой опроса узла
и смену его кода на уровне `WARN`, а повторы того же кода — на уровне `DEBUG`; успешный опрос сбрасывает эту историю.
Синхронный сбой вызова опроса и недоступность узла при отправке пишутся на уровне `WARN`. Описание ошибки в результате
проверки от этого формата не зависит.
Опрос запоминает объект наблюдения перед вызовом RPC и публикует ответ через `compareAndSet`: изменение кеша после
начала опроса не позволяет устаревшему ответу восстановить доступность. Признак незавершённого опроса снимается и
при отклонённом ответе, поэтому следующий опрос может обновить состояние. Политика исключения и восстановления
узла описана в [features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

`GrpcConfiguration` подключается приложением. Приложение предоставляет `TransactionOperations`
и доменные репозитории, включая `ContestRepository` и `TaskValidationRequestRepository`.
Источник узлов при запуске описан в разделе [Реестр узлов](#реестр-узлов). Закрытие контекста
прерывает поток отправки, останавливает `ExecutorService` и `ScheduledExecutorService`, отменяет RPC и закрывает
каналы. `removeNode` отменяет незавершённую попытку и возвращает контекст в очередь; повтор учитывает прежний лимит времени.

## Реестр узлов

`GradingNodeRegistry` хранит адрес и признак участия каждого Проверяющего узла через `GradingNodeStore`
из [settings](../settings/README.md#реестр-проверяющих-узлов). Требования к реестру определены в
[features.md](../../docs/domain/features.md#testsysdevgradingbalancing-implemented).

Менеджер разделяет наблюдение и участие. Монитор узла владеет каналом опроса и кешем статуса. Регистрация участия
владеет отдельным каналом проверки. Фоновый опрос обходит все мониторы, а выбор узла и `Grader.getNodeStatuses`
видят только зарегистрированные узлы. `addNode` создаёт монитор, если его нет, и новую регистрацию. Перед началом
участия статус монитора сбрасывается в `Unknown`, поэтому узел получает Посылки только после следующего планового
опроса. `removeNode` закрывает канал проверки и повторяет незавершённые попытки этой регистрации; монитор продолжает
опрос. Удаление из реестра дополнительно закрывает монитор. Повторное включение создаёт новую регистрацию, поэтому
поздние ответы прежней попытки отбрасываются.

Методы порта `Grader.addNode` и `Grader.removeNode` меняют только участие в работающем грейдере. Реестр, его
хранилище и `GradingNodeRegistry.overview()` их не видят, а `removeNode` оставляет монитор опроса открытым. Узлы
реестра меняются через `GradingNodeRegistry`.

При запуске `GrpcConfiguration` читает хранилище до создания координатора; ошибка чтения прерывает запуск. Все узлы
реестра наблюдаются, включённые регистрируются до запуска фоновой работы. При наличии хранилища `testsys.grading.nodes`
меняет реестр только при `testsys.grading.import-nodes=true`; без флага адреса конфигурации используются только для
импорта по запросу.

С флагом `GrpcConfiguration` дополняет прочитанный реестр. Адреса конфигурации вне реестра добавляются включёнными,
отключённые адреса конфигурации включаются, остальные записи не меняются. Адрес длиннее 255 символов прерывает запуск
до создания клиентов. Координатор сначала наблюдает и регистрирует итоговый набор, затем изменения записываются
в хранилище в порядке конфигурации; фоновая работа ещё не запущена. Ошибка создания клиента, исключение записи или
отказ хранилища прерывают запуск, а созданные каналы закрываются. Записи, зафиксированные до ошибки, сохраняются,
и следующий запуск читает их из хранилища. Удалённый из реестра адрес конфигурации следующий запуск с флагом добавит
снова.

`GradingNodeRegistryCoordinator` сериализует изменения и сначала выполняет обратимый шаг:

| Изменение | Порядок |
|-----------|---------|
| Добавление | Наблюдение и при участии регистрация, затем запись |
| Включение | Регистрация, затем запись |
| Отключение | Запись, затем `removeNode` |
| Удаление | Запись, затем `removeNode` и закрытие монитора |

Ошибка шага грейдера до записи даёт `Failed` без записи. Если хранилище отказало, потому что у адреса другая запись
или записи нет, изменение даёт `Failed`, а шаг грейдера, выполненный до записи, компенсируется. После исключения
записи координатор перечитывает реестр. Ожидаемая запись даёт `Applied`, прежняя — компенсацию шага грейдера
и `Failed`. Ошибка чтения или неожиданная запись дают `Uncertain`: шаг грейдера перед записью компенсируется,
отключение и удаление грейдер не меняют. После `Uncertain` все изменения и импорт возвращают `Uncertain`
до перезапуска. Писатель один, поэтому отдельный идентификатор записи не нужен.

`importPreview` сравнивает адреса `testsys.grading.nodes`, прочитанные при запуске, с известным реестром без проверки
доступности. `importNodes` добавляет выбранные адреса в порядке конфигурации с указанным участием. Адрес из реестра
получает `Rejected(AlreadyRegistered)` без изменения, адрес вне конфигурации — `Rejected(NotRegistered)`.
`Uncertain` останавливает импорт: оставшиеся адреса попадают в `notAttempted`, добавленные ранее узлы сохраняются.

Без хранилища, например в самостоятельном модуле, `ConfiguredGradingNodeStore` заполняет реестр в памяти адресами
конфигурации как включёнными. Изменения действуют до перезапуска.

## Состояние очереди

`GradingQueueMonitor` возвращает `GradingQueueSnapshot` за один проход по незавершённым запускам координатора без
блокировки проверки:

| Счётчик | Состояние |
|---------|-----------|
| `preparing` | `Preparing` |
| `waiting` | `Queued`, включая возврат после транспортного повтора |
| `grading` | `InFlight` |
| `saving` | `Saving`, включая ожидание повторного сохранения |

Каждый запуск находится ровно в одном состоянии, поэтому `total` равен сумме счётчиков. Завершённый запуск
в снимок не входит. Размер очереди отправки для счётчиков не используется.

## Настройки

Значения по умолчанию загружаются из [grading-defaults.properties](src/main/resources/grading-defaults.properties).
Приложение может переопределить их через Spring Environment. Интервалы задаются в формате ISO-8601 `Duration`.

| Свойство | По умолчанию | Назначение |
|----------|--------------|------------|
| `testsys.grading.nodes` | Пустая строка | gRPC-адреса Проверяющих узлов через запятую для импорта в реестр по запросу или при запуске с `testsys.grading.import-nodes`; без хранилища — начальный список узлов |
| `testsys.grading.import-nodes` | `false` | При `true` каждый запуск заносит адреса `testsys.grading.nodes` в реестр включёнными, см. [Реестр узлов](#реестр-узлов); без хранилища не действует |
| `testsys.grading.max-attempts` | `3` | Общее число транспортных попыток запуска |
| `testsys.grading.total-timeout` | `PT30M` | Срок подготовки, ожидания и проверки |
| `testsys.grading.rpc-timeout` | `PT10M` | Предельный срок отдельной проверки, ограниченный оставшимся общим сроком |
| `testsys.grading.status-timeout` | `PT5S` | Предельный срок опроса статуса |
| `testsys.grading.poll-interval` | `PT5S` | Интервал фонового опроса |
| `testsys.grading.max-message-bytes` | `400000000` | Максимальный размер входящего gRPC-сообщения |
| `testsys.grading.should-record-video` | `true` | Запрашивать видеозапись проверки |

Список узлов задаётся одной строкой в properties, YAML или аргументе командной строки приложения.
Например: `testsys.grading.nodes=grader-1:50051,grader-2:50051`.
Переменная окружения для того же списка — `TESTSYS_GRADING_NODES=grader-1:50051,grader-2:50051`.
Флаг задаётся так же: `--testsys.grading.import-nodes=true` или `TESTSYS_GRADING_IMPORT_NODES=true`. Он читается
только при запуске и не входит в каталог служебных настроек.

Пробелы по краям адресов удаляются, одинаковые адреса учитываются один раз. Пустая строка или строка из пробелов
означает пустой список. Пустой элемент непустого списка, в том числе после завершающей запятой,
останавливает запуск с ошибкой, содержащей имя свойства. Адрес передаётся gRPC как target без дополнительного разбора;
запятая внутри адреса не поддерживается. Список проверяется и при наличии хранилища, хотя без флага импорта реестр он тогда не меняет.

Порядок подключения узлов реестра при запуске описан в разделе [Реестр узлов](#реестр-узлов). До первого ответа
на опрос состояние узла — `Unknown`; доступность узлов при запуске не проверяется. Если создание клиента
завершается ошибкой, координатор закрывает уже созданные каналы и останавливает свои исполнители, а запуск
приложения завершается ошибкой. Список читается при запуске. Новые адреса конфигурации появятся в предпросмотре
импорта только после перезапуска.

## Резервирование и сохранение

Координатор резервирует идентификатор Посылки до загрузки данных. Репозитории сохраняют итог и обновляют текущий
статус Посылки в одной транзакции. Резерв снимается после фиксации транзакции, затем вызываются подписчики;
ошибка одного подписчика не мешает остальным. Откат метаданных не удаляет уже записанные внешним `FileBlobStorage` блобы.

Ошибка сохранения оставляет результат и резерв в памяти для повторного сохранения, без повторного RPC.
Повтор сохранения назначается отдельной одноразовой задачей через `pollInterval`.

## Сроки проверки

Общий срок отсчитывается от приёма запроса и задаётся одноразовой задачей. Предельный срок RPC ограничен оставшимся
общим сроком. Принятый результат сохраняется и после истечения срока, если хранилище временно недоступно.
Завершение отменяет таймеры.

Общий срок проверяется между задачами координатора. Если доменный репозиторий блокирует загрузку или сохранение,
проверка сроков других Посылок ждёт окончания этого вызова. Приложение должно ограничивать время запросов к хранилищу.
RPC и фоновый опрос используют собственные предельные сроки независимо от таких задержек.

## Хранение в памяти

Очередь, кеш статусов и защита от дубликатов живут в памяти одного экземпляра приложения. После перезапуска они
не восстанавливаются; реестр узлов восстанавливается из хранилища.

## Общие служебные настройки

При подключённом `RuntimeSettings` приём проверки фиксирует лимит попыток, общий срок, RPC-срок и видео.
Этот снимок живёт в `RunContext` во всех фазах и повторах. Повторный запрос незавершённой проверки его не заменяет.
Опрос готовит новое расписание до сохранения, а право запускать задачи получает при публикации снимка.
Следующий status RPC получает текущий timeout; уже начатый сохраняет прежний. Каналы и grade RPC не пересоздаются.
Размер входящего сообщения фиксируется при запуске для всех каналов, включая добавленные позднее.
Ожидание отправителя и новые таймеры сохранения читают текущий интервал.
Без общего holder модуль использует Environment. Источники и восстановление — в [settings](../settings/README.md).
