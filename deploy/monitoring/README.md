# Локальный мониторинг

Документ описывает локальный запуск Prometheus и Grafana рядом с TestSys, запущенным на той же машине: файлы
конфигурации, запуск, сбор метрик, хранение данных, учётные записи Grafana и дашборды. Он предназначен для
разработчиков, которые смотрят метрики TestSys у себя. Развёртывание на сервере документ не описывает: образ
приложения, общий compose со всей Системой, обратный прокси и публикация портов в него не входят. Имена и метки
метрик описаны в [monitoring/README.md](../../testsys-infra/monitoring/README.md), сервер метрик и HTTP-метрики —
в разделе [«Метрики»](../../testsys-web/app/README.md#метрики) app/README.md.

## Файлы

| Файл | Назначение |
|------|------------|
| `compose.yaml` | Сервисы `prometheus` и `grafana`, их образы, тома данных и порты |
| `prometheus/prometheus.yml` | Интервал сбора и адрес сервера метрик TestSys |
| `grafana/provisioning/datasources/prometheus.yaml` | Источник данных Prometheus с `uid` `testsys-prometheus` |
| `grafana/provisioning/dashboards/testsys.yaml` | Загрузка дашбордов из `grafana/dashboards/` в папку «TestSys» |
| `grafana/dashboards/*.json` | Дашборды |

Версии образов закреплены в `compose.yaml`.

## Запуск и остановка

Нужен запущенный Docker с Compose. Запустите TestSys по разделу
[«Запуск и проверка»](../../testsys-web/app/README.md#запуск-и-проверка) app/README.md, затем запустите стек
из корня репозитория:

```bash
docker compose -f deploy/monitoring/compose.yaml up -d
```

Остановите стек без удаления данных:

```bash
docker compose -f deploy/monitoring/compose.yaml down
```

Команда `down -v` удаляет тома, а с ними историю метрик и учётные записи Grafana.

Порты публикуются только на `127.0.0.1`. Другой порт задаётся переменной окружения или в файле `.env`
рядом с `compose.yaml`:

| Компонент | Адрес по умолчанию | Переменная |
|-----------|--------------------|------------|
| Grafana | `http://localhost:3000/` | `GRAFANA_PORT` |
| Prometheus | `http://localhost:9090/` | `PROMETHEUS_PORT` |

## Сбор метрик

Prometheus раз в 30 секунд запрашивает `GET /actuator/prometheus` у сервера метрик TestSys по адресу
`host.docker.internal:8082`. Порт совпадает со значением `testsys.metrics.port` в `application.yml` приложения.
Если TestSys слушает другой порт, измените цель в `prometheus/prometheus.yml` и перезапустите Prometheus:
переменные окружения в этом файле не подставляются.

```bash
docker compose -f deploy/monitoring/compose.yaml restart prometheus
```

Сервер метрик отдаёт метрики без сессии и служебного входа, поэтому Prometheus не нужны учётные данные TestSys.
Устройство сервера метрик и его свойства — в разделе [«Сервер метрик»](../../testsys-web/app/README.md#сервер-метрик)
app/README.md.

Опрос использует OpenMetrics 1.0.0. Приложение передаёт время регистрации счётчиков и HTTP-гистограмм в рядах
`_created`; Prometheus с флагом `created-timestamp-zero-ingestion` добавляет в это время нулевую точку.
Так первый замер со значением 1 даёт прирост от 0. Протокол закреплён в `prometheus/prometheus.yml`:
Protobuf-экспортер используемого client_java 1.7.0 передаёт это время у счётчиков, но пропускает у гистограмм.

После включения экспорта `_created` перезапустите TestSys. Изменение команды запуска Prometheus применяется
пересозданием контейнера с сохранением тома:

```bash
docker compose -f deploy/monitoring/compose.yaml up -d --force-recreate prometheus
```

Имя `host.docker.internal` ведёт из контейнера на машину, где запущен Docker; `compose.yaml` задаёт его через
`host-gateway`.

- На macOS с Docker Desktop эта схема проверена.
- На Linux `host-gateway` — адрес моста Docker на машине. Сервер метрик должен слушать этот адрес: значение
  `testsys.metrics.address` по умолчанию, `0.0.0.0`, подходит. Межсетевой экран машины должен пропускать
  подключения из сети Docker к порту метрик. На Linux эта схема не проверялась.

## Хранение данных

Prometheus хранит метрики 14 дней в томе `prometheus-data`. Grafana хранит пользователей, пароли и настройки
в томе `grafana-data`. Тома сохраняются после `down`, перезапуска контейнеров и Docker. Docker добавляет к именам
томов имя проекта: `testsys-monitoring_prometheus-data` и `testsys-monitoring_grafana-data`.

## Учётные записи Grafana

У Grafana свои учётные записи, не связанные со служебным входом TestSys. Самостоятельная регистрация и анонимный
доступ выключены.

При первом запуске Grafana создаёт администратора `admin` с паролем `admin`. Войдите им и сразу смените пароль:
Grafana предлагает это после первого входа. Остальных пользователей создайте в разделе Administration → Users and
access → Users.

## Дашборды

Grafana загружает дашборды из `grafana/dashboards/` в папку «TestSys». Дашборды обновляются раз в 30 секунд,
период по умолчанию — последние 3 часа. Сохранить изменения дашборда в Grafana нельзя: правьте JSON-файл
в репозитории, Grafana перечитывает его сама.

| Дашборд | Что показывает |
|---------|----------------|
| «TestSys — HTTP», `testsys-http.json` | Число запросов, группы кодов и отдельные коды ответа, среднее время и 95-й перцентиль; таблица точек входа за период. Фильтр «Интерфейс» выбирает основной или служебный интерфейс |
| «TestSys — ошибки операций и технические сбои», `testsys-failures.json` | Ошибки операций по родам и операциям, технические сбои по источникам, этапам и исключениям, повторы транзакций — отдельными панелями |
| «TestSys — проверка Посылок», `testsys-grading.json` | Результат опроса TestSys; очередь проверки по четырём этапам и общее число незавершённых проверок; узлы по участию и результату опроса; сообщённые узлами очередь и ёмкость; завершённые проверки по исходу |

На каждом дашборде переключатель «Сглаживание» выбирает окно расчёта: «Авто», «1 мин», «5 мин», «10 мин»
или «30 мин». Он влияет на графики частоты HTTP-запросов, среднего времени и 95-го перцентиля ответа,
ошибок операций, технических сбоев, повторов транзакций и завершённых проверок. Очередь, узлы, статус опроса,
итоги и таблицы за выбранный период от этого переключателя не зависят.

По умолчанию выбран режим «Авто»: Grafana использует `$__rate_interval`. При текущем интервале сбора 30 секунд
он равен `max($__interval + 30s, 120s)`. Значение `$__interval` зависит от выбранного периода и ширины графика:
при расширении периода окно обычно растёт, при приближении остаётся не меньше 2 минут.

Фиксированные окна не меняются при выборе периода. Чем больше окно, тем плавнее график и тем слабее видны
короткие пики. Окно «1 мин» при сборе раз в 30 секунд чувствительно к пропускам замеров: для расчёта нужны
хотя бы две точки, поэтому на графике возможны разрывы.

Таблица точек входа показывает для каждой точки входа число запросов, число и долю ответов 4xx и 5xx и 95-й
перцентиль времени ответа за выбранный период. Столбцы сортируются щелчком по заголовку; по умолчанию таблица
отсортирована по доле 5xx.

Коды HTTP-ответов, ошибки операций и технические сбои — разные срезы одних событий, поэтому дашборды их
не складывают. Требование — в [testsys.dev.metric.failures](../../docs/domain/features.md#testsysdevmetricfailures-implemented).

Числа за период — округлённый результат `increase`, частоты — результат `rate`. Это оценки по соседним замерам,
а не журнал событий. Ряды счётчиков создаются при первом событии; до него панели итогов показывают 0.
Первый прирост становится виден после успешного опроса, если нулевая точка `_created` и ненулевой замер попадают
в окно расчёта. Для короткого окна, пропущенных опросов и событий у границы периода возможны отличия от точного числа.

При перезапуске TestSys новые счётчики и гистограммы получают новое время регистрации. Prometheus может добавить
новый ноль даже при одинаковых значениях до и после перезапуска. Ноль должен предшествовать замеру и не нарушать
порядок уже сохранённых точек; слишком старое время, рассинхронизация часов или более поздняя точка прежнего ряда
могут помешать его добавлению. События процесса, завершившегося до успешного опроса, восстановить нельзя.
Включение настройки не исправляет старую историю. Перезапуск Prometheus с сохранённым томом не создаёт новое событие.

Панель «Опрос TestSys» показывает, отвечает ли сервер метрик: если он недоступен, остальные панели не получают
новых данных.

Автоматические оповещения не настроены.

## Ссылка из служебного кабинета

Кнопка «Grafana» на главной странице служебного кабинета открывает адрес из обязательного свойства
`testsys.service.grafana-url`, см. раздел [«Конфигурация запуска»](../../testsys-web/app/README.md#конфигурация-запуска)
app/README.md. Для этого стека значение — `http://localhost:3000/` или адрес с портом из `GRAFANA_PORT`.
Вход в Grafana выполняется отдельно.

## Проверка

1. Откройте `http://localhost:9090/targets`: цель `testsys` должна быть в состоянии `UP`.
2. Войдите в Grafana и откройте папку «TestSys». На дашборде проверки панель «Опрос TestSys» показывает
   «Доступен», на дашборде HTTP после нескольких запросов к TestSys появляются данные.
3. Запросите сервер метрик с заголовком OpenMetrics:

```bash
curl -H 'Accept: application/openmetrics-text;version=1.0.0' http://localhost:8082/actuator/prometheus
```

Ответ должен иметь тип `application/openmetrics-text`, заканчиваться `# EOF` и содержать `_created` для уже
созданных счётчиков и HTTP-гистограмм.

4. После запуска TestSys откройте один отсутствующий адрес основного интерфейса. Дождитесь успешного опроса.
   В таблице точек входа дашборда HTTP строка `NOT_FOUND` должна показать первый ответ 4xx; при единственном
   запросе этого ряда число запросов и число 4xx равны 1, доля 4xx — 100%. Выбранный период должен включать запрос.
5. Проверку первого события четырёх собственных счётчиков, HTTP-ответов 4xx/5xx и перезапусков выполняет
   `PrometheusIngestionTests` в `testsys-web:app`. Тест использует отдельные контейнеры и сервер метрик,
   читает конфигурацию и выражения дашбордов из этого каталога; пользовательские тома не затрагивает.

```bash
./gradlew :testsys-web:app:test --tests 'tech.testsys.bootstrap.PrometheusIngestionTests' -Pdetekt.autoCorrect=false
```
