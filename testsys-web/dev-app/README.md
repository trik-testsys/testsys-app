# Dev-приложение веб-компонентов

Документ описывает самостоятельный модуль `testsys-web:dev-app`: витрину компонентов и демонстрационные сценарии.
Рабочие страницы Кабинетов сюда не входят. API компонентов описан в [components/README.md](../components/README.md),
общая структура и сборка — в [structure.md](../../docs/project/structure.md).

Точка запуска — `DevApplication`, корень пакетов — `tech.testsys.web.devapp`. У приложения свои `AppShell`,
Spring-конфигурация, локаль, frontend и обработчик HTTP 404. Оно использует библиотеку components,
а не исходники или артефакт основного приложения. Большая фабрика текстов и визуальная реализация 404 общие.

## Устройство исходников

Пакет `showcase` содержит маршруты витрины. Страницы собирают классы `ShowcaseView`, `ShowcaseStatesView`,
`ShowcaseFormsView`, `ShowcaseOverlaysView`, `ShowcaseDisplayView`, `ShowcaseHeaderView`, `ShowcaseFoundationsView`
и `ShowcaseNestedView`; их секции вынесены в тематические файлы для раскладки, полей, действий, отображения,
навигации и живых обновлений.
Таблицы, фильтры полями, диалоги и lookup-примеры имеют отдельные файлы. Общие строки посылок и колонки
принадлежат `ShowcaseSubmissionSamples.kt`.

В `demo/model` находятся данные, fixtures, неизменяемое состояние, выбор доступных объектов и чистые переходы.
Авторизация, действия Организатора и проверка Решений разделены по файлам.
`DemoTableFilters.kt` содержит данные фильтрации и выбор страниц таблицы.
В `demo/ui` находятся страницы, формы, подписи, таблицы и `DemoNavigation.kt` с меню и ключами разделов.
`demo/DemoSession.kt` хранит состояние одного UI, выбор объектов и фильтры; она также запускает отложенную
демонстрационную проверку Решения. Тестовые пакеты повторяют это разделение.

## Отсутствующие маршруты

У приложения собственный обработчик `NotFoundView` в пакете `error`: штатный `HasErrorParameter<NotFoundException>`
с кодом 404. Визуальная часть общая — `NotFoundPage`, см.
[components/README.md](../components/README.md#приложения-и-общие-страницы). Страницы витрины и демонстрация
`/dev/demo` доступны только в профиле `dev`; вне него они переходят на экран 404.

`application.yml` также включает `vaadin.eagerServerLoad=true`, поэтому код 404 получает и первый HTTP-запрос;
следствия настройки описаны в разделе
[Отсутствующие маршруты](../app/README.md#отсутствующие-маршруты) основного приложения.

## Запуск и проверка

Команды запуска и сборки — в [structure.md](../../docs/project/structure.md#сборка-веб-приложений).

Витрина — примеры совместного использования и памятка существующих элементов, не эталон и не источник правил.
Правила оформления — в [ui-design.md](../../docs/project/ui-design.md), API и контракты — в components.
`/dev/showcase/foundations` иллюстрирует состояния движения и бренд из общих ресурсов.
Главная витрина — `/dev/showcase`; тематические маршруты — `states`, `forms`, `overlays`, `display`, `header`
и `foundations`, вложенный пример — `states/accessibility`.
Примеры сеточных колонок находятся в `showcase/ShowcaseSubmissionSamples.kt`,
трёх ролей действий только с иконкой — в `showcase/ShowcaseActionSections.kt`.
На `/dev/showcase/states` блок «Широкая матрица результатов» показывает 30 результатных столбцов и две страницы.
Блок «Таблица в выделенном блоке» показывает обычные строки, readonly поле, progress и pills внутри `highlightBlock`.
Контракт границы конфигурации — в [components/README.md](../components/README.md#граница-конфигурации).
Все иконки представлены на главной витрине; тематические страницы сохраняют поля, compact filters, состояния,
оверлеи, отображение и таблицы.
Блок «Скрытые значения» на `/dev/showcase/forms` показывает все семейства полей, информационный поток с действием,
readonly/disabled и общую привязку скрытия. Пример приёма файлов использует компактный загрузчик со скрытыми
именами. Контракт — в [components/README.md](../components/README.md#скрытые-значения).
Следующий блок «Скрытие без подписи» показывает компактные списки без внешнего поля: доступный и два
выключенных с разным порядком применения режимов, с общей привязкой скрытия и переключением доступности.

Правила текстов демонстраций — в [ui-design.md](../../docs/project/ui-design.md#текст-интерфейса).

## Демонстрация сценариев

`/dev/demo/:screen?` — Kotlin DSL на данных пакета `demo`. Ключи: `home`, `login`, `<role>.<section>`;
полный список разделов принадлежит `demo/ui/DemoNavigation.kt`. Меню содержит восемь Кабинетов.
URL и Back/Forward работают
через маршрутизатор Vaadin. Вкладки подразделов находятся под полным заголовком Кабинета в PageHead
и используют точное совпадение параметров маршрута. Короткие информационные поля показываются парами
на общей сетке, длинные описания и логи занимают строку; регистрация группирует псевдоним и Роль.
Заголовок Кабинета в меню ведёт в его Обзор; поиск открывает и фильтрует
ту же панель. Неизвестный ключ открывает Главную.

Fixtures и переходы принадлежат Kotlin demo model; данные и выбранные объекты живут в одном UI между разделами,
сброс возвращает fixtures. Модель не подключает БД, бизнес-операции или production security.
Результат действия показывает один стандартный toast успеха/ошибки из DemoContext. Сообщение не хранится
в UI-состоянии и не создаёт блок страницы; навигация, фильтры и фоновые обновления не повторяют feedback.
Ошибки полей остаются внутри формы, подтверждение регистрации сохраняет свой функциональный блок.
Вход по КД, регистрация Ученика/Организатора, подтверждение и одноразовое восстановление показывают mock письма
внутри демонстрации. Существующие Кабинеты сохраняют контекст Роли и сведения выбранных объектов.

Организатор создаёт Соревнование и Участников через Dialog из действий шапки соответствующего блока.
Количество — целое положительное, default 3; максимум 100 за вызов только для устойчивости демонстрации,
не лимит Системы. Добавление доступного существующего Тура имеет отдельный Dialog.
CSV содержит всю матрицу Участников и Задач выбранного Тура независимо от фильтра/страницы.

Все списки используют стандартные TableFilters, обычные поля/Binder и таблицу с pageSize 10.
Defaults пустые; фильтрация начинается с уже ограниченного контекстом набора.
Контракт применения, сброса и валидации описан в [components/README.md](../components/README.md),
раздел «Поля фильтров таблицы». Выбранные сведения находятся вне отфильтрованной таблицы. Период использует штатный dateRangeInput и календарь.
Результат Судьи сохраняет выбор Решения и сведения/логи/видеозапись; Наблюдатель и Организатор используют
одну матрицу лучших баллов: при небольшом числе Задач результатные колонки заполняют доступную ширину,
при большом — пример сохраняет все Задачи с локальной прокруткой. История Ресурса — таблица с фильтрами и скачиванием версии.
Footer общий. Отправка файла демонстрационная: содержимое не сохраняется, состояния Queue/Checking/Checked
меняются локально; скачиваемые материалы явно являются примерами.
Приём файла Решения находится в теле блока, действие отправки — в его footer.

Чистые сценарии модели и фильтрации проверяются в `src/test/kotlin/.../demo/model/`.
Тесты форм и маршрутов используют Karibu и находятся в `demo/ui/` и `showcase/`; общий тест построения
страниц `PagesTests` — в корневом пакете.

Cookie сессии называется `TESTSYS_DEV_SESSION`. Отдельное имя позволяет открывать оба приложения
на одном хосте одновременно без перезаписи сессии другого приложения.
