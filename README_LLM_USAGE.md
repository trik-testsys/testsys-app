# Использование LLM-инструментов

LLM-клиенты, например Claude Code/Codex и другие, используют общие
[проектные инструкции](AGENTS.md), скиллы и роли из `.testsys-agents/`. Подключение и обновление локальной конфигурации описаны в
[testsys-llm-sync.md](testsys-llm-sync.md), соответствия действий инструментам — в
[tool-mapping.md](.testsys-agents/tool-mapping.md). Правила разработки остаются в документации проекта.

## Начало работы

После клонирования откройте репозиторий в выбранном клиенте и попросите агента прочитать общие инструкции
и подключить конфигурацию. Ниже — примеры для Claude Code/Codex:

```text
Прочитай AGENTS.md и testsys-llm-sync.md, подключи конфигурацию TestSys для Claude Code в этом checkout.
```

```text
Прочитай AGENTS.md и testsys-llm-sync.md, подключи конфигурацию TestSys для Codex в этом checkout.
```

После подключения откройте свежую сессию. Проверьте, что клиент видит шесть скиллов из таблицы ниже без
дубликатов и шесть именованных ролей, а агент получает корневой `AGENTS.md`. Для проверки отдельного контекста
попросите запустить `coder` без задачи: он должен прочитать общую роль и сообщить о недостающих входных данных.
Подробные проверки и ограничения загрузки инструкций — в [инструкции подключения](testsys-llm-sync.md#6-verify-a-fresh-context).

Для другого клиента добавьте проверенный раздел в
[tool-mapping.md](.testsys-agents/tool-mapping.md#adding-a-client) и соответствующий раздел нативного
подключения в [testsys-llm-sync.md](testsys-llm-sync.md#1-select-the-client). Общие скиллы и роли остаются
едиными. Клиент должен независимо загружать `AGENTS.md` и общую роль в каждом отдельном контексте;
необходимые действия проверяются по его реальным инструментам и ограничениям. Подключение другого клиента
не считается готовым только по аналогии с примерами.

## Скиллы и роли

| Скилл | Роли | Назначение | Пример обычного запроса |
|-------|------|------------|------------------------|
| [implement](.testsys-agents/skills/implement/SKILL.md) | [coder](.testsys-agents/roles/coder.md) | Планирование задачи по гайдам, согласование решений, реализация и самопроверка со сборкой и тестами | «Реализуй задачу из `<файл-задачи.md>` с помощью implement» |
| [review-changes](.testsys-agents/skills/review-changes/SKILL.md) | [reviewer](.testsys-agents/roles/reviewer.md), [review-verifier](.testsys-agents/roles/review-verifier.md) | Строгое ревью незакоммиченных изменений, PR, коммитов или путей без правок исходников | «Проверь незакоммиченные изменения с помощью review-changes» |
| [fix-review](.testsys-agents/skills/fix-review/SKILL.md) | [fixer](.testsys-agents/roles/fixer.md) | Перепроверка и исправление выбранных замечаний отчёта, сборка и тесты | «Исправь замечания 1 и 3 из последнего отчёта с помощью fix-review» |
| [generate-localization](.testsys-agents/skills/generate-localization/SKILL.md) | [localization-generator](.testsys-agents/roles/localization-generator.md), [localization-reviewer](.testsys-agents/roles/localization-reviewer.md) | Добавление региона или заполнение недостающих переводов с `ru-RU`; существующие переводы меняются только по явному запросу | «Заполни недостающие переводы EN / en-US с помощью generate-localization» |
| [add-localization](.testsys-agents/skills/add-localization/SKILL.md) | Те же роли локализации | Создание и явное изменение исходных сообщений `ru-RU`, golden-проверки и независимое языковое ревью | «Добавь сообщение о числе оставшихся попыток с помощью add-localization» |
| [testsys-design](.testsys-agents/skills/testsys-design/SKILL.md) | — | Проектирование и реализация интерфейсов на Vaadin/Kotlin DSL и явно запрошенных самостоятельных макетов | «Спроектируй экран Кабинета с помощью testsys-design» |

Явный вызов в Claude Code — `/implement <файл-задачи.md>`, `/review-changes` или `/fix-review` с входными
данными после команды. В Codex используйте `$implement <файл-задачи.md>`, `$review-changes` или `$fix-review`,
либо выберите нужный скилл в интерфейсе клиента. Обычный запрос также может выбрать скилл по его назначению.
Порядок работы и форматы входных данных и отчётов находятся в общих файлах по ссылкам.

Для переводов используйте `/generate-localization EN / en-US` в Claude Code или `$generate-localization EN / en-US`
в Codex. Для исходных сообщений используйте `/add-localization <смысл и контекст>` или
`$add-localization <смысл и контекст>`. Ключи и параметры можно указать, если они уже выбраны. Генератор возвращает
человеку созданное MF2 и пояснение его устройства. Исследовательские заметки с источниками сохраняются в
`.testsys-agents/resoures/localization/<language-tag>.md` и повторно используются обеими ролями.

При создании сообщений в обычной задаче `coder` делегирует их генератору в apply и запускает отдельное языковое
ревью. Неоднозначности возвращаются основной сессии для уточнения. Добавление исходников может временно оставить
переводы неполными; итоговый отчёт различает эти ошибки, недоступные проверки и успешную сборку.

Обычная последовательность: `implement` подготавливает план и после утверждения меняет рабочее дерево;
затем `review-changes` проверяет результат; `fix-review` исправляет выбранные замечания. После исправлений
повторите ревью и просмотрите `git diff`. Агенты не делают коммитов и не публикуют изменения во внешние системы.

## Обновление конфигурации

После получения обновлений, изменения нативных настроек или создания нового checkout попросите агента:

```text
Прочитай AGENTS.md и testsys-llm-sync.md, синхронизируй конфигурацию TestSys для Codex в этом checkout.
Сохрани мои локальные настройки и посторонние ресурсы.
```

Для Claude Code замените название клиента. После синхронизации повторите проверку в свежей сессии.
Изменения общих сценариев и ролей доступны через ссылки; детали повторного подключения и разрешения конфликтов
принадлежат [testsys-llm-sync.md](testsys-llm-sync.md#5-synchronize-again).

`AGENTS.md`, `.testsys-agents/` и инструкция синхронизации хранятся в Git. Каталоги `.agents/`, `.claude/` и `.codex/`
целиком локальные и игнорируются Git; в них находятся подключения и личные ресурсы клиентов. Остальные
локальные ресурсы сохраняются. Если клиентские файлы уже отслеживаются Git, исключение не снимает их с учёта:
этот шаг выполняет пользователь при подготовке изменения к фиксации.

Технические ограничения зависят от клиента. Например, Claude Code подключает общие guard-скрипты нативными hooks в доверенной
сессии; Codex использует контракты ролей и доступные ограничения инструментов и среды. Полное совпадение защиты
клиентов не предполагается; подробности — в [справочнике инструментов](.testsys-agents/tool-mapping.md).
